# 每日作战执行

`tasks:auto_battle_dispatch_pc.yaml:auto_battle_dispatch_pc` 是唯一普通用户入口。
执行器先运行当天普通关卡，再运行构析勘探；不检查账号等级、关卡解锁或剩余挑战权限。
GUI 已接入周一至周日编辑，保存完整周计划；执行端仍在任务实际开始时选择游戏日。

## GUI 配置

作战终端上方选择要编辑的星期，普通关卡按列表顺序执行，每项可设置 1～9999 次，
并保留难度、编队和抓捕等原有参数。列表内可直接修改次数、复制、删除和调整顺序。
新增关卡的选项按所选星期的开放规则筛选，不检查账号解锁情况。

构析勘探单独配置，勾选类型后通过上移／下移调整优先级，无次数设置，固定最后执行。
战败和体力不足的停止规则是固定行为，不提供允许失败后继续打关的开关。
普通关卡和构析均为空的日期直接跳过作战，并继续工作流程后续步骤。

编辑修改自动保存完整七天计划。开始按钮执行今天的安排，切换编辑星期不会改变执行日。
工作流程作战设置显示今天的普通总次数和构析顺序，跨日后的执行配置由后台再次确定。
运行时锁定修改，结果按返回的游戏日展示，不把今天的结果写到另一天的任务行。

旧单日任务单按普通关卡开放日迁移到一周；无开放日限制的关卡每天保留，
原有构析任务转换为每天最后执行的类型顺序。已经保存的周计划不静默删除错误开放日选择，
用户可在列表中修正；执行端仍会拒绝不符合开放日的配置。

## 输入与游戏日

直接执行当天配置：

```json
{
  "jobs": [
    {"route_id": "ct.tie_an.shoggolith_city.bounty", "run_count": 3, "formation_index": 1}
  ],
  "structural_types": ["hetero_branches", "disordered_roots"]
}
```

`run_count` 为 1～9999 的整数，省略时为 1；每次确认实际开战才计入 started。
`capture_count` 仍表示本场抓捕数量，与作战次数无关。普通关卡保持任务单顺序，
一项次数执行完再进入下一项，不按 CT/GP 或玩法重新排列。

构析类型为有序、去重的列表：`disordered_roots`（乱序根须）、
`hetero_branches`（异构厄枝）、`echo_buoy`（混响浮标）、
`birch_buoy`（桦树浮标）。不设置次数，脚本不执行额外的勘测信标补事件操作。

每周配置使用 `weekly_plan`，不能与直接输入 `jobs`、`structural_types` 混传，
即使直接输入是空列表也不能混用。例如：

```json
{
  "weekly_plan": {
    "mon": {"jobs": [{"route_id": "gp.action_summary.global_supply.standard", "difficulty": 6, "run_count": 3}]},
    "tue": {"jobs": [], "structural_types": ["echo_buoy", "hetero_branches"]}
  }
}
```

缺少的星期视为空计划。也接受 `weekly_plan: {"schema_version": 1, "days": {...}}`。
后台任务实际开始时按国服上海时间 05:00 解析 `effective_date` 与 `weekday`，
本轮固定使用该日配置。前面流程耗时、后台排队和运行中跨日均不改写这份快照。

全境特供的开放星期来自客户端 `LevelGroupFactory` 60900013～60900018：
制式周一、救世周二、雅致周三、尖端周四、混沌周五、魔力周六，周日六类全开。
静态规则存放在 `battle_catalog.json` 的 `open_weekdays`，运行时不读取客户端源码。
错误的开放日配置会在操作游戏前拒绝，不擅自替换关卡。

旧 `jobs` 输入继续适配；其中构析 route 被提取为类型优先级，不参与普通次数循环。
旧 `stop_on_failure` 只接受兼容输入，不允许覆盖固定的战败／体力不足停止规则。

## 执行与返回

顶层 YAML 调用 `resonance_pc.execute_battle_plan`，Python 业务调度通过当前
`engine.bind_execution(context)` 执行完整内部任务和公共 action。
普通单场任务在关卡详情优先尝试原生扫荡；明确不支持扫荡才进入编队、实战与结算。
同一关卡连续扫荡留在已确认的详情页逐次操作，任务项结束后再返回主界面，避免重复导航。
原生扫荡每次执行一场，按用户配置的次数循环；只有奖励与返回页面均确认才计入 `swept`。
扫荡沿用普通任务的 `formation_index`，提交前确认已选队伍编号；省略时遵循游戏默认队伍。
扫荡入口必须正向识别，不以 OCR 没看到按钮作为不支持扫荡的证据。
提交后结果不明时保留已提交证据并报技术失败，不重复提交，也不转入实战补打一场。
提交前收到软停止会取消选队并回到原详情，提交后则等待本次奖励和回页确认，再结束流程。
构析使用游戏原生自动讨伐：配置有序类型，逐项确认优先级角标，启动一次，
之后由游戏选择事件与连续作战。脚本监督原生会话，发现结束条件时请求停止，
确认停止后返回勘测地图；不再逐场选择事件。异构厄枝的当前关卡仍由游戏页面决定。

普通作战确认战败或体力不足后停止剩余作战，包括尚未开始的构析。
构析原生会话观察到战败或体力不足时立即请求停止。原生连续开战与脚本观察存在时序差，
不能承诺第一次战败后绝不会再开启一场；确认原生已经停止才允许交接。
确认退出收尾后，任务正常返回 `status: stopped`，不能显示为所有关卡获胜。
用户软停止返回业务 `status: cancelled`、`continue_workflow: false`；硬取消继续传播框架取消。
未知识别状态、执行异常和收尾失败仍保留框架失败语义。
不能通过新建独立 scope 绕过取消继续点击。

返回 schema 为 `resonance_pc.battle_plan_result.v1`，包含：

- `status`：`completed`、`stopped`、`skipped` 或软停止收尾后的 `cancelled`。
- `stop_reason`：正常完成为空；提前结束为 `defeat` 或 `insufficient_stamina`；软停止为 `cancelled`；空计划为 `empty_plan`。
- `counts`：普通作战的 `planned/started/won/lost/swept/not_started`；`started/won/lost` 仅统计实际战斗，扫荡完成单独计入 `swept`，满足 `planned = started + swept + not_started`。构析的观察结果另存 `structural`，不与普通作战全量统计混算。
- `results`：关联原任务索引、场次和实际 outcome；保留已经完成的结果。
- `job_results`：每项关卡的请求次数、已开战／胜／败／扫荡／未执行次数，以及完成、提前停止或未执行状态。
- `cleanup.returned_to_main`、`continue_workflow`：主界面交接证据和允许接续标记。
- `effective_date`、`weekday`：本轮锁定的游戏日。

空计划不操作游戏，返回 `skipped/empty_plan`，`cleanup.required` 和
`cleanup.touched_game` 为 false，不虚报已返回主界面。
工作流程对这种明确跳过直接接续；其他正常／提前结束必须确认返回主界面。
接续前仍等待框架终态且 `execution_pending` 为 false，不允许旧 worker 与下一任务并行输入。

进度以当前任务 CID 隔离，状态键为 `resonance_pc.battle_plan.<cid>`，事件为
`task.resonance_pc_battle_plan_progress`。场中快照只保留末 20 条结果及总数，
避免随执行次数反复复制整份历史；终态保留完整结果。失败和取消保存现有进度后，
技术失败和硬取消继续传播原框架异常／取消；软停止返回取消业务结果，两者都不允许接续。

整份作战计划不继承 GUI 的通用短总超时。单场战斗、页面转场和收尾分别受有界预算控制。

## 构析原生自动会话

公共 action 仍为 `resonance_pc.run_structural_exploration`，输入仍为有序的 `types`。
配置阶段必须确认类型选择和优先级角标与请求一致，之后只启动一次原生自动。
监督阶段观察胜败、缺体力及无匹配目标等状态，不通过逐场重新点击事件接管游戏原生调度。
停止阶段确认原生自动已关闭，并确认回到 `world_scan`，才能报告可交接。

构析返回 schema 为 `resonance_pc.structural_native_result.v1`：

- `mode`：固定 `native_auto`。
- `outcome`：`completed`、`defeat`、`insufficient_stamina` 或 `cancelled`；`reason` 为对应原因，当前无匹配目标时为 `no_matching_targets`。
- `configured_types`：实际确认的有序类型，不以请求值代替角标确认。
- `native_stopped`：原生停止已经确认时为 true。
- `page_after`、`ready_for_next`：确认停止并回到勘测地图后分别为 `world_scan`、true。
- `observed.won/lost`：脚本实际观察到的胜败计数；`statistics_complete` 固定 false，不声称覆盖客户端全部作战，也不据此推算全部消耗。

用户取消时优先请求停止游戏原生自动，确认停止后结束当前工作流程，不执行后续任务。
`outcome: cancelled` 用于记录该次原生会话的退出原因，不能据此允许工作流程接续。
原生停止或回页未确认时按 `stop_failed` 处理，不返回可交接的成功结果。
技术异常同样不能伪装成正常完成、无匹配目标或已停止。

取消采用两阶段处理：第一阶段以根任务 CID 关联软停止请求，保留执行端完成原生停控和回页确认的机会；
正在执行普通作战时，会等待本场结束并返回主界面；构析会等待当前战斗回页并关闭连续自动。
第二阶段才确认任务取消并结束流程。内部参数 `control_cid` 用于关联这份请求，用户无需在 GUI 配置。
窗口退出期间的等待超时不会自动升级为强制取消；只有用户明确选择强制退出时才终止工作进程。
若软停止无法完成而进入强制取消，框架取消只证明脚本已停止，不能证明游戏原生自动已经关闭；
此时原生状态标为未知，不返回 `native_stopped: true`，也不允许启动后续工作流程任务。

## 实施范围与验收边界

新增／调整的 task 元数据、manifest 导出、内部返回和任务清单须同步维护。
运行时仅依赖计划包内的静态目录和识别素材；客户端文件与开发提取依赖不随任务加载。

2026-10-29 用户授权实机测试后，普通关卡实战获胜并返回主界面已完成两场，
其中第二次测试请求两场，在第一场中请求软停止，最终仅执行一场，剩余一场未启动。
两场合计消耗 80 澄明度，未补充体力或使用勘测信标；空计划跳过也已通过实际任务入口确认。
随后的扫荡测试在进入关卡前导航失败，未执行扫荡提交；之后用户关闭游戏，停止实机测试。

离线验收覆盖任务加载、manifest／任务层级契约、GUI 交接和取消，
并用 fake UI 覆盖扫荡单次提交、编队确认、体力不足、结果不明和停止收尾。
这些检查不代表实际画面的识别阈值、扫荡成功路径或构析原生会话已经实机通过。
仍待下次实机确认扫荡奖励与回页、构析类型优先级角标、原生启动与停止，
以及真实战败／缺体力后的收尾和后续流程接续。
