# OCR stage benchmark

此工具测量当前 PP-OCRv6 small 在真实截图上的稳定态耗时。
模型先完整加载并逐阶段预热，每张样本另外预热 3 次；默认两个独立进程顺序执行，
每轮每张样本交替执行 20 对开启/关闭计时的调用，共 320 次调用（160 次开启、160 次关闭）。
每次调用严格比较原始结果和解析结果的文字、置信度、框、中心点等字段，
并核对跨进程结果一致性。这不是带标注的准确率评估。

在仓库根目录运行：

```powershell
$stageTemp = Join-Path $PWD '.pytest_tmp/ocr-stage-benchmark'
New-Item -ItemType Directory -Force $stageTemp | Out-Null
$env:TEMP = $stageTemp
$env:TMP = $stageTemp
$env:TMPDIR = $stageTemp
$env:AURA_LOG_ROOT = Join-Path $stageTemp 'logs'
& ./.venv/Scripts/python.exe -m tools.benchmark_ocr_stages --output .pytest_tmp/ocr-stage-benchmark
```

固定 CPU 8 个 ORT 算子内线程、关闭算子内/间线程池自旋，OpenCV 线程策略保持原状。
输入为已有数字单行（99×25）、中文单行（280×44）、小区域（250×70）、
整屏（1280×720）四张真实截图或区域，前两组使用直接识别模式。
整屏检测继续使用长边 960 上限策略，小区域不主动放大。

时间包含图像转换、预处理、模型推理、后处理和 `OcrResult` 解析；
不含截图、文件解码、会话加载/预热、异步桥接、输出比较或计时报告构造。
CPU 采用同步 `session.run`，推理阶段按调用的墙钟时间测量，不代表累加的 CPU 时间。

汇总中五组互斥：

| 组 | 包含阶段 |
|---|---|
| detection | 检测预处理、检测推理 |
| orientation | 方向分类预处理、推理、旋转判断 |
| recognition | 识别排序/批次准备/预处理、识别推理 |
| postprocess | 检测后处理、裁图、CTC 解码、结果组装、结果解析 |
| other | 输入颜色转换、其余编排与计时开销 |

占比用所有调用的阶段耗时之和除以总耗时之和计算，相当于均值之比；
不能用各阶段独立的 P50 拼出总耗时。另保留每个细分阶段的均值和占比、
总耗时 P50/P95、关闭计时的配对基线，以及模型、样本和源码的 SHA256。
开启与关闭的耗时差包含调度噪声，不能将负差值解读为计时使推理加速。

原始数据位于 `.pytest_tmp/ocr-stage-benchmark/run-*.json`，逐次明细为 `calls.csv`，
汇总为 `summary.json` 和 `summary.csv`。同一输出目录再次运行会覆盖同名轮次文件；
保留不同实验时应指定新目录。可用 `--summarize-only` 重新汇总。

## 2026-10-22 本机结果

环境：Ryzen 9 9950X（16 物理核/32 逻辑处理器），Windows，ONNX Runtime 1.27.0，
CPUExecutionProvider，PP-OCRv6 small，ORT 8 线程/关闭自旋，OpenCV 32 线程。
四组样本在开启/关闭计时的全部调用和两个进程间，原始及解析结果均完全一致。

下表为每次调用的均值与对应占比。检测、方向分类和识别列包含各自预处理；
后处理列按上表口径包含检测后处理、裁图、CTC 解码、组装和解析。

| 场景 | 文本数 | 总均值 ms | 检测 ms / % | 方向分类 ms / % | 识别 ms / % | 后处理 ms / % | 其他 ms / % |
|---|---:|---:|---:|---:|---:|---:|---:|
| 数字直接识别 | 1 | 7.87 | 0 / 0 | 0 / 0 | 7.37 / 93.6 | 0.38 / 4.9 | 0.12 / 1.5 |
| 中文直接识别 | 1 | 6.82 | 0 / 0 | 0 / 0 | 6.38 / 93.5 | 0.35 / 5.1 | 0.10 / 1.4 |
| 小区域完整 OCR | 3 | 27.88 | 3.84 / 13.8 | 5.86 / 21.0 | 16.10 / 57.7 | 1.87 / 6.7 | 0.22 / 0.8 |
| 整屏完整 OCR | 40 | 571.08 | 91.44 / 16.0 | 70.02 / 12.3 | 378.62 / 66.3 | 28.52 / 5.0 | 2.48 / 0.4 |

总耗时 P50/P95（ms）分别为：数字 7.86/9.87，中文 6.57/8.70，
小区域 25.16/43.92，整屏 521.54/882.26。整屏两轮均值分别为 621.84 和 520.33 ms，
绝对耗时有明显波动，但识别占比为 66.9% 和 65.6%，方向分类为 11.8% 和 12.9%。
不宜将本轮绝对耗时与先前 CPU 线程基准直接作为性能回归比较。

细分后，小区域识别推理本身为 15.81 ms，整屏为 372.86 ms；
对应方向分类推理为 5.72/66.64 ms，检测推理为 3.73/88.97 ms。
整屏 CTC 解码为 20.30 ms，识别预处理为 5.77 ms，说明主要瓶颈在模型推理，
优先减少识别输入补零与优化批次，比只优化 Python 后处理更值得调查。
对方向确定的 UI，独立跳过方向分类可尝试省去该阶段约 21%（小区域）或 12%（整屏）的开销，
这些只是已测阶段占比，实际开关后的收益仍需复测。

计时开启相对关闭的均值差为数字 -0.24 ms、中文 +0.34 ms、小区域 -1.09 ms、
整屏 +34.49 ms。差值正负不一且整屏方差较大，不能据此精确估算计时器自身成本，
默认仍关闭。现有分阶段证据不支持优先改线程默认值或再次调整检测上限；
建议先验证短文字识别宽度及宽度感知批次，再评估独立方向分类开关。
