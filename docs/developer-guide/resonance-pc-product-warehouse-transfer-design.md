# 整顿中心成品仓取出到车厢方案

更新日期：2026-10-24。当前实现采用**商品图标模板识别类型、OCR 读取数量、独立的页面与目标连接状态检测控制点击**。取货仅处理当前可见完整商品格，不回顶、不上下拖动或滚轮，也不滚动复扫。此前识别修复后的涤纶实机记录见文末；这些记录来自含滚动的旧版流程，不作为本次无滚动版本的实机验收。

## 范围与输入

起点和正常结束页面都是普通监狱（整顿中心）总览，游戏客户区为 1280×720。调用方负责先停靠云岫桥基地、不处于旅行。只从成品仓取货到列车，保留车厢已有货物。

| 业务输入 | 规则 |
| --- | --- |
| `goods`：指定货物类型 | 按名称或身份解析为商品 ID；未传、`null`、`[]` 表示尝试当前可见的全部达标商品，重复项去重 |
| `quantity_threshold`：数量阈值 | 非负整数，默认 1；仓内数量必须为正且 `>= quantity_threshold` 才可取 |

非法名称、无法解析的指定类型和非法阈值在游戏输入前拒绝，不能把无效的指定清单当成全拿。阈值是筛选条件，不是精确取货配额：仓内 20、阈值 30 时跳过；仓内 20、阈值 20、车厢只余 5 时可以点击，由游戏装入 5。

保留以下约定：

- 总览左下仓库入口只点击一次，随后检测是否进入，不补点。
- 列车↔成品仓连接、返回总览等其余界面切换，均有状态检测和有限补点。
- 按默认最大模式取货，不检测或切换最大模式，不进入定量弹窗。
- 每次只点击一个符合条件的成品栈；取货点击不套用界面切换的补点规则。
- 每个商品 ID 本轮最多点击一次；每次点击后使用新截图重新定位，可继续处理删栈后自然进入视口的新格子，不主动翻屏。
- 首轮取货结束后，仅对当前视口做一次只读稳定复查，再正常返回总览；复查不再取货。
- 车厢装满是正常结束，允许成品仓仍有余货。
- 不接收菜、交订单、出售、卸货或再次生产；业务输入仍只有上述两项。

## 总体流程

```mermaid
flowchart TD
    A["货物类型、数量阈值"] --> B["确认监狱总览，单击仓库入口"]
    B --> C{"仓库页已出现？"}
    C -->|否| X["停止，记录失败和已知结果"]
    C -->|是| D["检测并设置列车↔成品仓连接，必要时有限补点"]
    D --> E["读取载货量，保留当前视口"]
    E --> F["新截图：识别当前可见完整格子，目标数量交给OCR"]
    F --> G{"车厢已满？"}
    G -->|是| K["结束首轮取货"]
    G -->|否| H{"有达标且尚未处理的目标？"}
    H -->|是| I["记录身份和原数量，只点击一栈"]
    I --> J{"新截图确认搬运效果？"}
    J -->|否| X
    J -->|是| R["记录变化，丢弃旧坐标，重新定位列表"]
    R --> F
    H -->|否| S["停止：no_visible_eligible_goods"]
    S --> K
    K --> L["当前视口只读稳定复查一次，不滚动、不取货"]
    L --> M["按已确认的同一商品前后数量核算新增装车数量"]
    M --> N{"本次搬运及数量可确认？"}
    N -->|否| X
    N -->|是| O["左上返回，检测总览，必要时有限补点"]
    O --> P["返回本次新增货物及数量"]
```

连接或返回超时同样进入失败结果。图中的一次复查只确认停止时的当前视口，不代表全仓覆盖；取货期间点击后的变化检测和重新定位，不开启第二轮取货。

## 各步骤如何识别

| 对象 | 识别方式 | 用途与约束 |
| --- | --- | --- |
| 监狱总览、仓库入口 | 固定区域的事项一览、仓库快捷图标模板 | 确认入口所在页面，单击后等待仓库页 |
| 仓库页面 | 列车载货、原料仓、成品仓固定文字的灰度结构模板，加共享返回键 | 三个标题均须命中；不依赖标题亮暗、其他仓库是否连接或目标按钮状态 |
| 列车↔成品仓连接 | 先用灰度按钮结构定位，再在锚点内固定偏移处比较选中／未选中彩图 | 颜色状态独立且互斥，未选中不推断另一组连接；缺失、冲突或不匹配保持未知；已经连接时零点击通过 |
| 商品类型和格子位置 | 原生商品彩图与前景掩码匹配，比较前两名候选分差 | 从完整 84×84 格子取 `[8,24,68,42]`，避开角标、数量和白条；身份按商品 ID 记录 |
| 商品库存数量 | 紧裁数量区域，调用现有 OCR 的 recognition-only 模式 | 只对目标类型读取数量；未限定类型时读取全部候选，不通过数字模板复核 |
| 列车载货量／容量 | 独立固定区域 OCR，解析 `当前量/上限` | 校验范围，判断车满；不使用商品格子的整数解析器读取分数 |
| 空仓辅助标记 | 成品区 EMPTY 模板、容量读数和列表观察 | 辅助确认空列表；单次未匹配到商品不直接等于库存为零 |
| 返回总览 | 仓库页面内定位共享 `GLOBAL_BACK`，点击后识别总览特征 | 每次补点前确认仍在仓库，目标已出现就不再点击 |

商品模板采用 masked `TM_CCOEFF_NORMED`，校正分数门限 0.81、候选分差 0.10。仓库页三个固定标题及目标连接按钮锚点采用灰度 `TM_CCOEFF_NORMED`，门限 0.92，不施加颜色误差条件。按钮内部选中／未选中状态采用彩图 `TM_SQDIFF_NORMED` 转相似度，门限仍为 0.90、平均颜色误差上限仍为 18；没有统一放宽门限。状态裁片相对按钮锚点偏移 `[4,12]`，尺寸 `[32,135]`，不独立搜索其他位置。

页面与目标连接分别返回：`page=warehouse` 可以同时存在 `tp_connection=unknown`。目标连接为 `selected` 时内部 `connection=train_product`，明确 `unselected` 时为 `not_train_product`；其余为 `unknown`。准备阶段仅在仓库页明确且目标按钮明确未选中时点击，不再要求先确认原料仓↔成品仓连接。旧亮／暗标题模板仅作诊断，不参与页面或连接授权。

商品目录已生成 225 款彩图与掩码；供图覆盖 30 款，只有 ID113「涤纶」有仓库侧证据，其余已观察款来自列车侧。生成成功与截图校正状态分开记录，识别歧义不能猜成指定类型。

## 商品数量 OCR

数量入口为 `_prison_warehouse_quantity.py::WarehouseQuantityReader`，配置为 `data/meta/prison_warehouse_quantity_ocr_pc.json`，路径均相对 `plans/resonance_pc/`。

| 项目 | 当前约定 |
| --- | --- |
| 输入 | 同一轮观察中完全可见的 84×84 RGB 商品格子 |
| 主裁剪 | 格内 `[7,65,76,16]`，收紧纵向，横向保留完整数量框 |
| 备用裁剪 | 主结果不合格时，在同一格子图上改用 `[7,66,76,15]`，只再读一次 |
| OCR 调用 | 原图、无额外预处理；`recognition_only=True`，关闭方向判断及旋转 |
| 数量解析 | 恰好一条完整 ASCII 正整数 `[1-9][0-9]*`，有限置信度不低于 0.80 |
| 不可读结果 | 返回未知，保留原始文字、分数和两次尝试；不当成 0 或达标 |

不删除字母凑数字，不做 `O→0` 替换，不拼接多个文本结果，也不按当前截图最多两位来限制数量位数。OCR 服务异常向上传递；服务失败不触发区域重试。一次读数最多两次 OCR，没有新的游戏输入或等待界面变化。

本批 72 个正常格子经实际读取器离线核对：亮态 47/47、暗态 25/25，0 错读、0 拒识，共 73 次 OCR，仅一格使用备用裁剪。该结果用于供图校正，未作实机验证。人工破损不参与当前方案选型或验收；原生数字和旧截图数字模板仅保留为历史资料。

## 界面切换与补点

仓库入口仍为一次点击。连接切换与返回总览共用以下规则：

1. 用新截图先识别源、目标状态；目标已稳定时直接通过。
2. 源页面和控件都明确时才点击；输入回执不作为切换成功依据。
3. 点击后等待界面响应，再截图检测。目标状态连续两帧确认。
4. 只有仍稳定停留在原状态、同一控件可重新定位、且尚未出现目标或明确过渡状态时，才允许补点。
5. 一旦观察到目标或明确过渡状态，锁定本次切换，不再追点，只等待稳定。
6. 默认首点 1 次、最多补点 3 次，整个切换共用 20 秒总时限；等待时长按实机调整。次数或总时限耗尽就报告该步骤失败。

连接和返回的目标证据分别是「列车↔成品仓连接已选中」和「普通监狱总览已出现」。不能因一次没识别到目标就盲点；返回时已经离开仓库，就不能沿旧坐标再次点击。

OCR 的备用裁剪是同帧图片重读；界面补点则必须重新观察游戏状态。两者独立，均不能转化为重复取货点击。

## 首轮取货与列表处理

### 1. 准备

校验输入，确认总览，单击仓库入口并检测仓库页。设置列车↔成品仓连接，读取列车载货量，直接保留成品列表当前视口，不确认顶部或底部，不发送列表拖动或滚轮输入。

界面客户区统一为 1280×720。此前四张带标题栏原图先裁 `[1,31,1281,751]`（XYXY）；本次稳定截图原图按 `[26,56,1306,776]` 裁客户区，不缩放。每张图的裁剪与原图哈希记录在控件目录和素材来源清单中，不能将整图坐标直接当成游戏坐标。

### 2. 当前视口筛选

在新截图中定位当前可见完整格子并识别商品 ID。指定类型时只读取相应目标的数量；未指定时尝试当前可见的所有可识别类型。身份、OCR 数量和点击位置必须来自同一轮观察，屏外或不完整格子不作为可点击候选。

首次取得该类型的可信库存读数时保存 `before_quantity`，在其首次取货点击前必须已有这个基线；后续重定位不覆盖初值。筛选条件为：类型匹配、数量为正、达到阈值、该 ID 尚未点击。数量未知或身份歧义的格子不点击，记录未识别项，不能据此宣称没有目标。

### 3. 点击一栈并确认

按当前界面顺序选择第一项达标目标，只点击一次。等待界面响应后重新截图，按商品 ID 观察库存减少、列表变化及适用的载货量变化，确认搬运效果；效果不明时停止，不补点该商品。

空栈会删除并重新排序，所以每次点击后丢弃旧格子索引和坐标，重新识别当前视口；保留已点击的商品 ID，本轮不再点击该 ID。删栈后自然进入视口的新完整格子可以继续处理，不回顶或主动翻屏。单个格子不再可见不等于库存为 0，点击后的数量必须有明确证据才能记账。

### 4. 可见范围与停止

当前视口没有达标且尚未处理的候选时，以 `stop_reason=no_visible_eligible_goods` 停止首轮，不再滚动查找。这个原因只描述当前可见范围，不声明屏外没有商品。点击或等待界面变化后都重新截图，不能把旧坐标或旧 OCR 读数带入下一轮输入。

车厢满时以 `stop_reason=train_full` 正常停止首轮，允许有余货。两种停止均只进行下面的一次当前视口只读稳定复查，不因复查发现余货而恢复取货。

## 复扫、数量核算与返回

1. 首轮结束后，仅对停止时的当前视口做一次只读稳定复查，重新识别可见目标及剩余数量 `after_quantity`。不回顶、不拖动、不滚轮，不点击任何物品，也不因仍有达标货物而开启新取货轮次。
2. `scan_scope="visible"`；`scan_complete` 仅表示当前可见范围已确认，不表示全仓覆盖。`inventory_complete` 仅在成品区明确为 EMPTY 且没有未知项时为 `true`，其余均为 `false`。商品未出现在当前视口不能据此记作库存 0。
3. 对本轮已点击且搬运效果确认的商品，按同一身份计算：

   `taken_quantity = before_quantity - after_quantity`

   前后数量以每次点击的确认记录及可见复查证据为准；屏外未见商品不能补成零。正 EMPTY，或无滚动且前后无阻断未知项、点击商品消失并由原有邻居顺序前移的稳定证据，可以确认该次删栈后的余量为 0。不能把点击前整栈数量当成实际装入量，也不能把列车最终总量或总增量分摊给各商品。普通货物可用载货量增量辅助核对；不占货舱的物品不强制满足这一等式。已点击商品的数量仍未知时必须失败，不盲目返回。
4. 车满时仍有余货属于正常结束；未达到阈值的余货正常跳过。复扫后仍有达标余货且车厢有空间时，报告未取尽，不再自动取货。
5. 本次搬运及新增数量明确后，执行左上返回的检测与有限补点，确认回到普通总览，再输出结果。正常流程不额外重进仓库。

同商品出现负差值、超过来源数量或相互矛盾的观察时，标记未知并保留证据，不取绝对值或猜测修正。未点击货物的读数未知与已点击货物的搬运结果未知应分别记录，不能将两者混成库存为零。

返回或切换仓库组合会触发游戏的 `DealWithGoods` 提交暂存调拨，因此取货过程中保持连接组合，最后按正常返回收尾。返回已确认与服务器强制回读是不同证据，不为等待提交而重放搬运或自动重进仓库。

## 结果与异常

主要输出为 `goods_taken`：**本次从成品仓新增装入车厢的货物及实际数量**，同类型合并，不包含车厢原有货物。剩余目标、可见扫描范围、停止原因和返回状态作为诊断记录，不另扩展成完整库存报表任务。

以涤纶仓内为 20、搬运后成品区明确 EMPTY 且无未知项、列车载货量从 74 增至 94 为例，本次结果为涤纶 20，而非涤纶 94：

```json
{
  "success": true,
  "status": "completed",
  "stop_reason": "no_visible_eligible_goods",
  "scan_scope": "visible",
  "scan_complete": true,
  "inventory_complete": true,
  "goods_taken": [{"goods": "涤纶", "quantity": 20}],
  "returned_to_overview": true
}
```

| 情况 | 处理 |
| --- | --- |
| 车厢满，复扫和返回完成 | 正常成功，停止原因为 `train_full`，允许有余货 |
| 当前视口没有达标且尚未处理的目标，复查和返回完成 | 正常成功，停止原因为 `no_visible_eligible_goods`，取货清单可以为空；不声明屏外已取尽 |
| 当前视口有未识别格子、可见范围确认不完整或有空间却仍有达标余货 | 记录部分完成及具体原因，不宣称全取尽；正常收尾需本次已搬运数量可确认 |
| 已发出取货点击但效果不明，或已取数量无法核算 | 停止新输入，不重放点击或整项任务；保留已知取货及未知项，不自动返回提交未确认的搬运 |
| 连接或返回次数／总时限耗尽 | 报告具体失败步骤；返回失败仍保留已确认的取货结果，不能假报已回总览 |
| 用户取消 | 停止新输入，保留当前页面和已暂存变化，不在取消处理里自动返回或继续提交 |

数量未知不填 0。成功表示本次约定操作与收尾完成，不表示成品仓已经清空或服务器库存经过强制回读。

## 实现与调用

| 内部步骤 | 职责 |
| --- | --- |
| `prepare` | 输入校验、一次进入仓库、连接检测与补点、容量基线及当前视口观察 |

任务名为 `withdraw_product_warehouse_to_train_pc`，公共动作为 `resonance_pc.withdraw_product_warehouse_to_train`。复用现有截图／输入服务、共享返回键与点击坐标处理，以及公共 `TransitionProbe`、`TransitionPolicy`、`run_transition` 机制；商品目录、控件目录和数量 OCR 各自独立。不改收菜任务，也不新增 GUI 或用户业务参数。

其他任务通过标准引用调用，例如：

```yaml
transfer:
  action: aura.run_task
  params:
    task_ref: tasks:withdraw_product_warehouse_to_train_pc.yaml:withdraw_product_warehouse_to_train_pc
```

`goods: []` 表示尝试当前可见的全部达标商品，不要求屏外全取；任务输入的 ID 写成字符串，例如 `["113"]`。直接调用公共动作也支持单个名称或 ID。已知不受模板目录支持的指定商品会在游戏输入前拒绝。
