# OCR 识别算子与现用数字资源分析

本报告记录的是 90°旋转仍默认开启时的诊断结果。后续默认关闭及固定框对照见
[OCR tall-crop benchmark](./ocr-tall-crop-benchmark.md)。

2026-10-22。本轮只增加独立诊断工具和报告，没有修改框架 OCR 链路、模型文件或默认配置。
模型、元数据、默认配置与相关源文件均记录 SHA256；测量前后保持一致。

## 实验口径

- Ryzen 9 9950X，Windows，仓库 `.venv` Python 3.12.10，ONNX Runtime 1.27.0 CPU。
- 仍为 PP-OCRv6 small、ORT 8 线程、关闭自旋、`ORT_ENABLE_ALL`；OpenCV 保留 32 线程配置。
- 识别宽度为 legacy，自适应分批；完整模式默认保留检测和方向分类。
- 沿用数字单行、中文单行、3 行小区域、40 行整屏四个真实来源 fixture。
  另加入个人面板澄明度和货舱 ROI、工坊比例、便当恢复量二值图、工坊编号模板、
  便当页疲劳 ROI，合计 10 项 profiling 输入。最后一项沿用现调用方的 3× INTER_CUBIC 放大。
- 两个串行独立进程，每项正常管线计时 20 次、算子采样 5 次、各预热 3 次。
  共 400 次正常管线测量、100 次识别工作负载采样；后者包含 150 次实际识别模型调用，
  另有 90 次 profile 会话预热调用被排除。
- 正常管线计时与算子采样分开。正常计时不包括截图、图像文件读取、加载、预热、
  异步桥接、结果指纹构造。记录阶段计时及输入形状有少量诊断开销。
- 通过临时观察器复制正常管线实际送入识别会话的 float32 tensor，记录形状、次序和哈希；
  profile 会话复放完全相同的输入。没有替换图、缩减字符集或更改图优化级别。
  每批完整概率输出与参考会话做字节 SHA256 比较，全部一致。
- 只累计实际执行的 `Node/*_kernel_time`，按 `model_run` 区间对应调用，排除预热，
  不叠加 session、executor、fence 等外层事件，避免重复计时。

原始图末端为 `MatMul.12`（120→18710）→`Add.204`→最终 `Softmax.2(axis=2)`。
实际 CPU 图中分类头为 `MatMul.12/MatmulTransposeFusion/`（FusedMatMul）与独立 Add，
最终 Softmax 仍独立。归组同时核验算子类型与末维 18710 的输出形状。
其余网络包含卷积、注意力、序列计算、归一化、激活、布局转换等；其中注意力的
`Softmax.0/1` 属于网络前段，不能算成最终 Softmax。

## 算子结果

以下百分比的分母是 **profile 识别 kernel 总耗时**，不是完整 OCR 总耗时，
也不是无 profiling 时的精确阶段占比。

| 输入 | 主干及序列部分 | 分类投影与偏置 | 最终 Softmax |
|---|---:|---:|---:|
| 数字单行 `258/286`，直接识别 | 88.41% | 8.61% | 2.98% |
| 中文单行，直接识别 | 88.31% | 8.55% | 3.14% |
| 小区域，3 行 | 81.29% | 12.82% | 5.89% |
| 整屏，40 行 | 76.65% | 13.90% | 9.45% |
| 个人面板澄明度，完整 OCR | 88.83% | 8.29% | 2.88% |
| 个人面板货舱，完整 OCR | 88.52% | 8.43% | 3.05% |
| 工坊 `7/7`，直接识别 | 88.58% | 8.50% | 2.93% |
| 便当 `51` 二值图，直接识别 | 87.51% | 9.41% | 3.07% |
| 工坊 `01` 模板，完整 OCR | 89.77% | 7.69% | 2.54% |
| 便当页疲劳比例，3× 完整 OCR | 88.63% | 7.89% | 3.48% |

整屏两轮分别为：主干 76.84%/76.43%，分类头 13.52%/14.33%，Softmax 9.64%/9.24%。

整屏单次工作负载六批累计的 profile 均值：主干 150.30 ms，分类头 27.27 ms，
最终 Softmax 18.53 ms，kernel 合计 196.09 ms。分类头中，矩阵投影 13.24 ms，
偏置 Add 14.03 ms，因此不能把分类头耗时全部说成矩阵乘计算。

主干内部按运行时算子类型累计：Conv 91.83 ms（全部 kernel 的 46.8%）、
Gelu 16.12 ms（8.2%）、ReorderInput/Output 共 12.89 ms（6.6%）。
这是运行时融合后的算子分类，Conv 可能已融合其他操作，不能回推为原始图逐节点的独立成本。

同批正常测量的整屏总均值 308.46 ms、识别推理 177.56 ms、识别解码 13.07 ms。
Profile 的 `model_run` 约 200.62 ms、Python `session.run` 约 201.52 ms；两者都与正常测量分开。
小输入的相对记录开销更大，例如数字单行正常识别推理 4.68 ms，profile kernel 6.52 ms。
不能把上述百分比直接乘以正常识别耗时当作无 profiling 的精确分摊。

两轮部分阶段记录到了其他 Python 进程的 CPU 活动，环境不是完全隔离。
当前结果适合判断瓶颈排序；不据此承诺优化可节省的精确毫秒数，也不作为与旧实验的严格提速对比。
`normal_background_cpu`/`profile_background_cpu` 仅审计同期 Python 工作负载，不覆盖全部系统进程。

## 现用数字模板与真实来源小图

样本清单含 92 项：62 张现用模板、25 张真实来源小图、同一疲劳 ROI 的 1×/3× 两项输入、
3 个带符号 ROI。不是 92 个独立运行场景。真实来源小图中，9 张便当恢复量样本已经二值化，
不能称为保留原始界面背景的截图。

62 张模板包括气泡水次数 7 张、仓库数量 10 张、便当恢复量两种样式各 10 张、
便当计数 13 张、工坊编号白色/灰色各 6 张。排除 mask 和未接入的开发用字形库。
工坊 `number_1` 到 `number_6` 的标签是 **`01` 到 `06`**，根据元数据中的原始文字确认，保留前导零。

每项执行以下三种模式，并各重复一次核对解码结果、置信度、框与解析结果稳定性：

1. 完整 OCR：默认检测、方向分类、识别。
2. 保留检测，只关闭方向分类。
3. `recognition_only=True`：输入整体作为正向单行识别。

没有添加字符白名单、补边、图像增强、文字清洗或降低识别阈值。
除当前调用方已有的疲劳 ROI 3× 输入外，模板与小图均原尺寸送入现有管线。

| 样本组 | 完整 OCR 正确 | 只关闭方向分类 | 直接识别正确 |
|---|---:|---:|---:|
| 现用数字模板 | 46/62 | 46/62 | 62/62 |
| 真实界面裁图：个人面板、工坊比例、便当计数 | 16/16 | 16/16 | 16/16 |
| 真实来源便当恢复量二值图 | 8/9 | 8/9 | 9/9 |
| 疲劳比例 ROI，原尺寸/3× | 2/2 | 2/2 | 2/2 |
| 带符号真实区域 | 3/3 | 3/3 | 3/3 |

每个正确项均为单个输出区域与标签严格相等；不依赖拼接多个区域才能判对。
模板的 16 个完整 OCR 失败包含 7 个空结果和 9 个错字；7 个空项均未进入识别回调，
应定位到检测及其后处理链，而不是识别置信度过滤。

明确错例：

- 气泡水模板 `6`→`9`，置信度 0.99383；仓库 `9`→`6`，0.97537。
- 便当计数模板 `6`→`9`，0.99021；`9`→`6`，0.98447。
- 二值真实来源 `41`→`47`，0.97778；直接识别为 `41`，0.99970。
- 三种模式中，两种完整模式的文字结果对全部 92 项相同。
  因此关闭 0/180 方向分类没有解决这些错误。

利用已保存的检测多边形和原图重建实际几何裁图（没有再运行推理）后发现：
气泡水 `6` 的透视裁图为 18×44，仓库 `9` 为 11×19，便当计数 `6` 为 7×11。
它们都满足现有 `_get_rotate_crop_image` 的高/宽≥1.5 条件，被自动顺时针旋转 **90°**，
随后方向分类没有将其旋转 180°。便当单字 `7`→`2` 同样触发此规则。
这是与 `use_textline_orientation` 开关独立的几何旋转，直接识别模式会绕过这段裁图逻辑。

`41` 则被检测为倾斜四边形，重建后的透视裁图只有 15×9，没有触发 90° 旋转；
原输入为 22×16。它说明裁图范围与重采样本身也会影响极小文字，不能把所有错误归结为同一条旋转规则。

直接识别虽然在本批样本全部文字正确，置信度并不总高：工坊黄色 `7/7` 仅 0.80888。
调用方若要求 0.9 仍会拒绝该结果。因此“文字正确率”不等于具体业务阈值下的通过率。
本轮疲劳 `324/856` 在 1× 和当前 3× 输入均正确，只能说明这一张 ROI 的结果。

## 结论与下一步

识别网络前段是最大的执行成本；18,710 类分类头与 Softmax 确实有开销，但没有占据大多数时间。
后续输出约简实验只应作为候选：图尾 ArgMax/Gather 不会自动删除分类投影、偏置和完整 Softmax，
不能把分类头与 Softmax 合计的 23.35% 宣称为可获得的提速。

对数字使用效果，更直接的问题是完整 OCR 对小字的检测、透视裁图和自动竖排旋转。
已知正向单行数字 ROI 可优先评估已有的直接识别选项；本轮并未修改任务调用，也不据此整体替换模板匹配。
默认方向分类、识别宽度、分批策略、CPU 线程数和自旋配置均保持原状。

## 工具与原始记录

在仓库根目录执行，工具启动子进程时会把 TEMP/TMP/TMPDIR 放在输出目录的 `tmp` 下：

```powershell
.venv/Scripts/python.exe -m tools.benchmark_ocr_operators `
  --output .pytest_tmp/ocr-operator-profile/final `
  --extra-samples .pytest_tmp/ocr-operator-profile/profile-extra-samples.json

.venv/Scripts/python.exe -m tools.probe_ocr_numeric_samples `
  --samples .pytest_tmp/ocr-operator-profile/numeric-samples.json `
  --output .pytest_tmp/ocr-operator-profile/numeric-final
```

上述清单是本轮保留的输入 artifact；不传 `--extra-samples` 时算子工具只执行原始四组 fixture。

- `.pytest_tmp/ocr-operator-profile/graph-evidence.json`：原始模型末端结构、权重维度。
- `final/run-{0,1}.json`：设置、哈希、输入形状、正常逐次计时、预热/采样调用映射。
- `final/operators-*.json`：原始 ORT trace，可用兼容 Chrome trace 的工具打开。
- `final/summary.json`：三组归因、逐批耗时、各算子汇总、两轮占比。
- `numeric-samples.json`：标签及其依据、路径、ROI、缩放与样本组。
- `numeric-final/numeric-results.json`：276 条模式结果，每条额外重复确认一次，共 552 次调用。
- `numeric-final/crop-diagnostics.json`、`crop-inspection.png`：具体错例的几何裁图证据。
- `analysis-manifest.json`：最终工具、清单、结果和报告哈希。

`pilot/` 是采集工具试跑；`main/` 是早期进程审计错误中止的数据，均不参与最终汇总。
最终结论只使用 `final/` 与 `numeric-final/`。
