# 识海深潜：视觉反馈观察方案

更新：2026-09-27。状态：已提供快慢视觉分离的连续扫描入口，当前棋盘5次实机完整扫描通过；跨布局可靠性尚未验收。

同日后续：已新增[魔方布局扫描实验任务](resonance-pc-deep-dive-scan-test.md)，用于用户实机人工比对。最新实机记录为54/54格、30.3–48.1秒（5次同棋盘复测）；原设计的跨布局可靠性目标仍需独立验收。

入口：[完整布局扫描设计与外部方案调研](resonance-pc-deep-dive-full-layout-design.md) · [实施计划](resonance-pc-deep-dive-visual-feedback-implementation.md) · [另一台机器接续](resonance-pc-deep-dive-visual-feedback-handoff.md)。

## 目标与决定

采用“受限短拖动 → 新鲜画面的结构反馈 → 择优关键帧 → 六面格子融合”。不再继续枚举快、中、慢灵敏度参数。每次拖动的响应都可能变化，因此最近一次测得的增益只用于约束下一小步。

第一版仍可寻找接近已有四个标准观察姿态的范围，复用原有素材；不要求按累计像素精确到位。随后升级为按六面的实际覆盖和清晰度决定采样、补扫与停止。最终输出统一的 `(face, row, col)` 及玩家、Boss、灵感位置，供后续计算使用。

2026-09-27 后续需求确认：玩家、奇点、灵感互斥，不会同格。目标语义为 `none / player / singularity / inspiration`，历史模型的 `empty / boss` 分别适配为无目标/奇点。低置信度、不可见、归属冲突属于“未知观察”，不能当成无目标。玩家与奇点分别需要唯一可信归属；灵感允许多个格子。

完整布局还需要识别无目标格的节点图标；目标格下方的图标无需识别。目标与图标分别记录，完成条件、表面字典、扫描坐标和现有实现适配以[完整布局扫描设计](resonance-pc-deep-dive-full-layout-design.md)为准。

本分支最初只保存方案，后续新增实验扫描入口。已有[简单随机移动](resonance-pc-consciousness-deep-dive-simple-random-walk.md)、[事件处理](resonance-pc-deep-dive-event-runtime.md)、[循环运行](resonance-pc-deep-dive-loop.md)继续作为现有实现基线。

## 游戏逻辑依据与证据边界

以下为设计阶段保存的客户端只读分析、字节码比对和关键控制流反汇编结论；后续实机记录见扫描操作说明。版本指纹见[接续说明](resonance-pc-deep-dive-visual-feedback-handoff.md#客户端证据指纹)。换客户端版本需重新检查，不能把这些结论视为永远不变的接口。

| 入口/对象 | 已观察到的逻辑 | 对方案的影响 |
|---|---|---|
| DragHandle.OnMouseDrag | 当前鼠标位置减上次位置；横纵分量分别乘旋转系数与 Time.deltaTime；以 Space.World 旋转 | 总位移相同不保证总转角相同，不能仅按三个档位解释 |
| Controller.OnEnter | rightDir 设置为相机的 right 方向 | 竖向拖动轴与相机有关；不能直接把任意步长当作严格一维轴角 |
| DragHandle.OnMouseUp | 关闭拖动标记并停止声音 | 该处理器未保存角速度或做释放后惯性更新；仍须等待输入消费和其他动画结束 |
| CubeRogueMain_Btn_Auto_Click / RotateToFaceUp | 根据当前玩家所在面选择六种目标姿态之一，插值到终点 | 重置是本次扫描的参考，不是跨回合恒定世界面 |
| SetCameraToMove | 约 0.5 秒内改变相机位置和 FOV；选择入口也可能重置视角 | 选格、旋转预览、镜头过渡不能混入扫描；0.5 秒不是稳定判定 |
| ConfirmRot / cube.rotate | 真正的游戏层旋转还更新格子数据和回合状态 | 必须区别观察旋转与改变棋盘状态的操作 |
| OnCubePointerDown/Drag/Up | 拖动事件转发；hasDrag 阻止抬起选格 | 移动选择状态下，未形成有效拖动的短按可能选格，不能任意用 1px 手势试探 |
| RubikCube / rolePos / TagFactory | 格子有 face/row/col；实体挂在 rolePos，存在偏移和缩放 | Boss 图像范围不等于格子表面范围，须按朝向处理浮空目标 |

简化的小步响应为 `Σ(本回调鼠标位移 × 旋转系数 × 本帧 deltaTime)`。这是解释响应变化的近似关系，不是通用精确轴角积分。固定帧率等条件下可出现距离与转角近似成比例，但不能推广到动态帧率。反编译器曾将 rightDir 的回退表达式误写为条件分支，关键语义已按字节码复核为 `rightDir or Vector3.right`。

实际模型使用预制资源。不能仅使用备用 GenerateFace 代码中的尺寸宣称已经标定渲染几何。

## 状态、控制与识别分工

### 1. 状态门禁和扫描代号

只在玩家可行动、普通棋盘稳定、没有事件覆盖、移动选格或旋转预览时扫描。通过正常 UI 重置，等待结构稳定，再建立扫描代号 epoch。

玩家移动、游戏层旋转、事件、敌方行动、自动对准、相机模式切换或状态不确定时，旧观测失效。不同 epoch 的格子证据禁止融合。已有事件流程的就绪与退出规则继续生效，不能用“棋盘像素稳定”替换所有业务状态判断。

### 2. 串行短步闭环

首版同一时间最多一个输入命令。流程为：记录输入前有效帧 → 执行一个受限短段 → 确认得到后续新帧 → 测量格线/角点变化 → 决定下一步。不能将长拖动拆成后台排队的短命令后称为闭环。

- 位移过大：缩小下一步；过冲后小幅反向修正。
- 位移很小：先排除旧帧、输入尚未消费、遮挡和跟踪丢失，禁止用近零增益反算巨大输入。
- 跟踪正常：逐渐增加步长；接近清晰姿态或置信度下降时收紧。
- 跟踪丢失：停止输入，重新定位；有限次恢复失败则重置或返回未完成。
- 取消、超时和异常：可靠释放鼠标，禁止遗留按下状态。

滚动增益及其变化范围只帮助限定下一步。必须有独立的输入位移、持续时间、在途命令、总扫描时间和恢复次数上限。参数由实机测量确定，当前不预设已经有效的像素值或反馈频率。有限视觉延迟下，增益突然变化仍可能过冲，设计必须允许容差和恢复。

保持按下、分段移动可作为后续优化，但要先验证输入后端与截图时序。鼠标接近边界时释放、移回安全起点再继续；不能把未观察到的动作当成已知转角。

### 3. 结构跟踪与关键帧选择

控制层跟踪格线、角点、块轮廓、可见面面积和倾斜程度。Boss 红光、玩家动画、灵感环不作为结构稳定的唯一依据。分类仅在清晰关键帧执行，避免每步推理 54 格阻塞反馈。

第一阶段以标准姿态附近的合格范围作为目标，采集数张不同时间的稳定帧。后续按照每个面的观察质量择优更新覆盖表。面身份无法确定的帧不计入覆盖。

使用已知魔方拓扑和标定几何，不从零实施通用三维重建。垂直转一圈不等于看清六面：必须验证六个不同面及各格的有效覆盖。仅当竖向路径无法获得所需观察时，加入受控水平修正。

### 4. 格子裁切和目标归属

必须分别保存格子表面多边形、实体可能伸出的范围、实际分类裁切区域。Boss 浮空偏移随面朝向改变投影，统一扩大矩形只是基线，不能替代归属校准。必要时利用相邻视角确认目标属于哪个表面格子。

分类输入需要与模型训练约定一致，包括 RGB、格子遮罩、尺寸、归一化、类别顺序。透视矫正表面不代表浮空实体也能按同一平面正确变换。

融合分数时同时考虑分类置信度、视角质量、可见性和跨帧一致性；不无限取所有帧中最大的 softmax。重复相邻帧不能当作独立证据。Boss/玩家竞争候选差距不足或面编号不确定时返回未知并补扫。

只有确认所声明坐标系下的面编号、行列方向、跨面邻接和当前 epoch，结果才允许交给接受该坐标系的规划器。首版可使用完整布局设计中的 scan_local；需要游戏内部编号的消费者必须通过显式映射。历史 V1L/V1R 等观察槽位不是游戏世界坐标。

## 方案比较

| 方案 | 优点 | 局限与定位 |
|---|---|---|
| 每个灵敏度一套四角度参数 | 简单，能复用固定裁切 | 对拖动期间响应变化脆弱；保留作历史采集基线 |
| 每次探测后一次大拖动 | 比固定表适应性好 | 探测后增益仍可能变化；只能作为短步估计 |
| 单纯缓慢持续旋转 | 容易采到中间画面 | 仍有帧率项，可能漏面、漂移或帧与输入错位 |
| 短步反馈、选择关键帧 | 可发现过冲、漏面、状态变化并恢复 | 需要可靠结构跟踪、帧时序、面身份和故障处理；推荐主线 |
| 通用三维重建 | 可处理未知场景 | 本场景已有拓扑约束，成本与不确定性偏高 |
| 可选只读姿态遥测 | 可能降低图像姿态估计难度 | 当前未证实桥接具备接口，需要独立设计和版本验证 |

锁帧可用于诊断，不能替代闭环。现有输入桥接保留 DragHandle 的响应语义；ScrollRect.StopMovement 不适用于这个魔方处理器。直接设置 transform 或调用内部业务方法改变了正常输入操作边界，不作为默认路线。
