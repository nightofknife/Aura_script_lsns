# PC 识海深潜：移动后事件的通用分流与处理器

状态：基于本机 2026-09-25 游戏配置、Lua 字节码的只读分析以及已收到的实机截图。确认卡预分类器和只读探测任务已实现，单局任务对未接入类型会安全停下；各类事件后续处理器仍待逐一实现及实机验证。普通／精英战斗已有五张后续页面样图和[战斗子流程设计](resonance-pc-consciousness-deep-dive-battle-flow-design.md)。事件名称、选项策略和已收素材见[事件响应设计](resonance-pc-consciousness-deep-dive-event-response-design.md)。

## 确认移动前：用节点介绍卡预分类

用户补充的七张截图表明：点击目标格后、最终确认“进入”前，右侧 `Group_EventDetails` 会先显示节点类型。控制器从 `ActivityListFactory.typeId` 读取 `TagFactory.eventTypeName`、描述和图标；没有事件数据时使用单独的“空白”文案。由此可以在点击“进入”前记下 `predicted_flow`，并为单类流程测试设置明确的前置条件，不必靠方块颜色猜类别。

本地 `TagFactory` 还列有“位面奇点战斗”，预期也交给战斗处理器；目前没有这一类介绍卡的实机截图，不把它计入已验证的视觉分类。七张新截图和旧的“小玩意儿／莫测漩涡”截图共九张介绍卡，离线匹配时公共“进入”按钮均达到门槛；非战斗卡用**标题＋固定类型图标**交叉核验，普通／精英战斗卡则用**稳定标题＋进入按钮**，不要求敌人头像匹配。所试的六张棋盘、领取页、选项页、商店页负例没有误达到“进入”按钮门槛。在原图及 80%、120% 亮度模拟下，原有 **33/33 项静态判断符合预期**；新增的实机精英头像和变化头像回归也通过。动画、不同界面缩放或更新后资源仍需实机复核。

已落地的只读入口 `tasks:consciousness_deep_dive_entry_card_probe_pc.yaml:consciousness_deep_dive_entry_card_probe_pc` 只检查 **1280×720 客户区当前是否有确认卡、七类中的哪一类**，返回 `{status, kind, confidence, score_margin, evidence_mode, enter_point, scores}`；不会点击“进入”。非战斗卡须同时通过公共“进入”按钮、标题和固定图标；战斗／精英战斗卡因头像可变，要求“进入”按钮与高分、明确领先的类型标题。证据不足返回 `absent` 或 `ambiguous`。原单局任务已直接接入普通／精英战斗的进入、开战、胜利、中间奖励和领取返回链，回棋盘后继续旋转；“小玩意儿／莫测漩涡”仍保持已有入口行为，其他未接入类型停下留图。

预分类只回答“**预计下一类是什么**”，不能替代移动后的真实画面：移动返回的被动奖励可能先弹出；剧情、过渡或结果页也可能插在主流程之前。如果点击“进入”后出现的稳定页面与 `predicted_flow` 不符，先交给通用页面识别器判断是否为合法前置／后续页；无法解释时停下留图，不沿用预测类别的点击坐标。

## 分两层，而不是按节点颜色写脚本

商店响应已直接接入原单局任务：识别 `shop` 确认卡并点击“进入”，进入 `shop_wait`，同时匹配顶部“无休之所”与左上返回箭头，连续两帧确认后只点击返回一次。接着进入 `shop_return`，持续确认魔方、玩家行动、移动已完成和旋转可用，再记录 `{type: shop, status: completed, purchased: false}` 并回到 `rotate_ready`。两个阶段各有30秒超时；返回后仍显示商店时只等待，不点商品或购买区域。已有[另一组商品的样图](images/resonance-pc-deep-dive-simple/37-shop-exit-only-alternate-stock.png)用于验证不依赖商品内容／尘埃数量；尚未自动实机验证商店链。

游戏的 `ConfirmToCube` 会发起移动。移动完成后，先可能处理移动响应自带的奖励，再进入格子对应的事件。`RogueEventFactory.func` 对主事件的分派只有四类：`OpenLevel`（战斗）、`Reward`（直接奖励）、`OpenUI`（独立界面）、`Options`（选择事件）；也可能没有待触发的事件而直接推进回合。介绍卡可以**提前选定预期处理器**，实际动作仍以**移动后出现的稳定页面**为准。

| 第一层：格子主流程 | 可能看到什么 | 通用处理器 | 不该做的假设 |
| --- | --- | --- | --- |
| 无事件或只发生被动效果 | 移动动画后回棋盘；可能先有奖励／数值提示 | `direct_move`：等待过渡结束，核实移动完成与后续步骤；若先出现提示，交给提示处理器 | 入口卡消失或短暂露出棋盘就算完成 |
| `OpenLevel` | 组队／战斗准备、战斗、胜负与奖励 | `battle`：交给战斗流程，直到胜负及后续页面确认 | 战斗页继续点击魔方坐标 |
| `Reward` | 一张或多张领取／失去展示页；可能有三选一、溢出替换 | `reward_queue`：每次只处理当前弹窗，关闭后重新分类 | 领取页固定只有一张，或点一次空白必回棋盘 |
| `OpenUI` | 休息、强化、招募、复活、觉醒、商店等独立界面 | `special_ui`：按该界面的安全路径操作或退出，再回到总分流器。商店只执行左上角返回 | 所有独立界面共用一个返回按钮 |
| `Options` | 1～4 项奇遇选项；选中态和条件不足态 | `option_event`：选项过滤、第一次选中、第二次确认，然后把效果后续交回总分流器 | 选项一确认就等于事件结束 |

这一层的 `Reward`／`OpenUI`／`OpenLevel` 只是**事件入口类型**；第二层的选项效果仍能再次引出奖励、战斗或另一事件。因此主流程与结果页必须解耦。另有一个跨类别的剧情门槛：`TryTriggerEvent` 对尚未看过的 `firstPlotId` 会先打开 `UI/Dialog/Dialog`，剧情页关闭后才继续触发事件。它需要独立的 `story_dialog` 处理器，不能误判为事件已完结。

## 第二层：确认选项后会发生什么

选项的 `optionFuncList` 在 `RogueOrderFactory` 中形成有序效果命令。当前控制器可见的命令类型包括 `Level`、`Reward`、`Discard`、`LoseBuff`、`LoseEquip`、`Intensify`、`Recover`、`Action`、`StepNum`、`SpinNum`、`Event`。一个选项可有多个命令，服务器返回也会带来奖励；下表描述**可能出现的页面类别**，不是每个选项都固定按这些行排序。

| 效果类别 | 典型后续页面或变化 | 共用处理器与完成信号 |
| --- | --- | --- |
| 无额外效果／纯叙述 | 选项消失，展示事件结束文字，随后回棋盘 | `narrative`：文字／动画稳定后一次空白点击；重新分类，不能直接记移动成功 |
| 直接获得／失去尘埃、骰子、推力或物品 | `ShowItem` 或 `ItemGet` 展示，标题如“恭喜获得”“失去” | `reward_notice`：确认标题及退出提示后点一次安全空白；可能连续多张，继续重拍 |
| 需要选取／丢弃一个或多个对象 | `ItemSelection`，候选卡和 `已选/所需` 计数 | `item_selection`：识别所有候选、点需要数量，核验计数达标后点“确定”；再识别扣除／获得结果 |
| 强化 | 可能先校验可强化对象，再显示强化结果或物品页 | `item_selection` 或 `reward_notice`；条件不足的选项在奇遇页已灰掉，不点击 |
| 生命变化 | `HpTips` 或直接数值动画 | `hp_notice`：只识别和等待效果完成；按当前约定**不检查选择前血量** |
| 总回合、移动或旋转次数变化 | 行动步骤数字动画，可能随后仍是原奇遇页 | `step_effect`：只在效果已确认后更新账本。当前策略硬排除改变移动次数的选项，暂不主动选额外旋转；不能靠一次点击推断计数已改 |
| 战斗 | 组队页／战斗／胜负／奖励 | `battle`：完成整段战斗及其后续，再回总分流器 |
| 链到下一事件或打开另一独立界面 | 新介绍卡、新选项页、商店／休息页等 | 再次进入第一层分流；设置最大深度和超时，不能按上一事件标题继续点击 |
| 物品超出容量 | `RogueItemReplace` | `item_replace`：选定保留／替换对象并确认；没有明确策略时停下 |

控制器的 `TryShowReward` 会依次显示奖励队列；队列空了还可能打开溢出替换。每个子页面关闭后，`OnPanelBack` 才决定继续显示下一份奖励、继续执行剩余效果命令、恢复选项页、进入下一事件或推进回合。`OptionOver` 还会显示选后叙述，关闭选项页后 `TryShowNextRound` 可能把游戏带到棋盘、敌方阶段、下一回合奖励或结算。**所以不存在一个对所有节点适用的固定“点击次数”。**

独立页面关闭时，控制器有时会显示一个继续按钮，再根据保存的 `continueType` 执行 `StartEvent`、`OpenOptionPanel`、`OpenSquadPanel`、`NextRound`、`NextFace` 或 `EndCube` 等不同动作。这个 `continue_prompt` 也应按实际画面单独识别；点击后重新进入总分流，而不是直接宣告返回棋盘。

## 一个总循环，多个小处理器

运行时保留 `pending_move`，每次只根据**最新一帧稳定页面**执行一个动作，然后重拍并重新分类：

```text
移动目标被接受
  → 介绍卡：认出“进入”后点击一次
  → 观察当前页面
      结算：立即终止本局
      动画／加载：等待，不点击
      选项页：过滤不可选及移动次数变更 → 选中 → 同项确认
      物品选择页：选择到要求数量 → 确定
      奖励／失去／回血提示：按本页提示关闭一次
      事件结束叙述：待稳定后关闭一次
      首次触发剧情或继续提示：交给剧情／继续处理器
      战斗／独立界面／物品替换：交给对应处理器
      商店：仅点击已识别的左上角返回箭头，不购买
      新事件：从介绍卡／新选项页重新分流
      棋盘：确认事件链已结束且移动步骤生效，再提交 pending_move
      未知：保存画面并停止
```

通用观察结果建议包含 `{page_kind, confidence, title, option_rows, selected_row, selectable_rows, selected_count, required_count, exit_prompt, frame_id}`。每个处理器返回 `{action_taken, expected_next_kinds, confirmed, event_effects}`，其中 `confirmed` 只能在**动作后的新画面**验证，不能等于点击函数返回成功。结算检测始终优先于其他页面。对于棋盘，需避开移动动画中短暂露出的画面：持续稳定、事件覆盖层消失、移动步骤状态更新并进入可操作阶段后，才能结束本次移动事件。

空白点击也属于受控动作：只在明确识别到可退出的奖励／扣除／叙述页时点一次；若下一帧仍是同一页，先判断文字是否只被加速、动画是否还在播放，再决定是否再点。连续奖励按队列逐页关闭，不对屏幕盲点固定两次。

## 现在能否判定正在走哪个流程

用现有 17 张**未标注的原始界面截图**和一张单局实机保存的地板塌陷页，做了离线页面分类试验：17 张均与人工页面标签一致，地板塌陷归入通用 `option_list`。识别不是看具体奖励图案：获得／失去页用标题加底部退出提示，选项页用“奇遇事件”标题加右侧卡片轮廓，已选态另看青蓝高亮；物品选择页用“可选择数量”及计数区域，商店用页面标题，棋盘和结算沿用各自的画面标志。八音石结束叙述与选项页**共用“奇遇事件”标题**，必须再判断右侧是否有选项卡，不能只靠标题。

| 战斗进行中／战败、其他休息／独立页、剧情、继续按钮、溢出替换、回血提示、单局胜利结算 | 尚缺对应后续页样图 | 游戏逻辑能列出分支，**当前不能可靠判定这些后续页** | 遇到时留图，后续再开放会继续点击的子任务 |

上述“17 张一致”只证明**给定样本中的静态区分**，不能证明动画帧、不同分辨率、未来活动资源或未见页面也会正确。未知类别、两个类别同时高置信、界面尚在动画中，都应保持 `unknown` 并等待或留图，不靠节点颜色猜测。

## 怎样独立测试每个处理器

已先实现上述**确认卡只读探测任务**，可以安全检查当前节点的预分类。下一步需扩展一个独立的**后续页面只读探测任务**，在任意当前界面返回 `{page_kind, confidence, candidates, frame_path}`，不点击；它负责验证进入后落到战斗、奖励、选项或其他页面。随后用同一个受控测试任务传入 `expected_start_kind` 和 `flow_kind`（例如 `entry_to_next_page`、`option_event`、`item_selection`、`reward_notice`、`narrative`、`shop_exit`），只运行对应处理器，**一旦识别到不同的稳定页面就返回 `next_page_kind`，不自动接管下一类处理器**。`entry_to_next_page` 从七种已知介绍卡开始，点击“进入”后只判定它实际到达的第一种页面，适合逐类测试节点路由。

这使一条长链可以分段测：在八音石选项页运行 `option_event`，它停在“失去推力选择”；再从该页运行 `item_selection`，停在“失去”展示；再运行 `reward_notice`，停在结束叙述；最后运行 `narrative`，停在棋盘。黄色节点则从 `reward_notice` 开始，下一页可以直接是棋盘。紫色自动工坊从 `option_event` 开始，下一页是“恭喜获得”。商店 `shop_exit` 只点左上返回。这些子任务不读写完整局的移动回合账本，便于重复验证某一页的点击和后续判别。

每个子任务都应先校验当前画面恰好属于 `expected_start_kind`；不匹配就原地返回，不尝试“帮用户进入”目标页面。每次发出一个点击后只等待**页面状态变化并稳定**，记录预期与实际下一类别；同一页面没变化时不盲目重试。若下一页仍属同类（例如连续奖励），返回“同类下一页”，可再次运行该处理器；完整单局任务日后再把这些处理器串起来。结算可随时抢占任何子任务。

## 实施边界与验收

配置用于预测某个选项**可能**引出哪些效果，视觉识别决定**现在**显示什么。优先实现总分流器、选项页的两次点击、奖励队列、选择／丢弃页、叙述退出；这几类已经有实机样图。`OpenUI`、战斗、溢出替换各接独立处理器，在没有识别／完成证据时返回 `unsupported_event`。一项配置若同时包含奖励和战斗，处理器按游戏实际显示顺序逐页消费，不新增该选项专属脚本。

验收用例至少覆盖：无事发生直接回棋盘；直接奖励只有一页和连续多页；一项可选／多项可选／不可选；选项无后续、直接奖励、选择后奖励、扣血提示、战斗、连锁事件；奖励队列后溢出替换；商店只点左上返回且无购买；事件中途出现结算。当前版本对任何 `StepNum`（改变本回合移动次数）选项一律不选；若没有其他可用选择就停下留图。不要求识别当前血量。
