# PC 识海深潜：简单版随机游走需求

状态：需求记录，尚未实现。此版本独立于[多角度棋子定位方案](resonance-pc-consciousness-deep-dive.md)，先完成简单的随机游走与重复开局。具体的回合状态与任务编排见[简单版移动循环设计](resonance-pc-consciousness-deep-dive-simple-loop-design.md)。

## 目标

进入识海深潜后，在玩家行动阶段从蓝框可选格子中随机选一个移动。有事件就先完成事件，再随机执行一次游戏旋转；等待敌方阶段结束，进入下一回合。失败或胜利出现结算画面后退出结算，重新开启一局。

## 一局内的行为

1. 进入[初始魔方画面](images/resonance-pc-deep-dive-simple/01-board.png)，等待“玩家行动中”。新开局时清空本局移动记录和已完成回合数。
2. 点击右侧“移动”，等待[蓝框可选位置](images/resonance-pc-deep-dive-simple/02-move-options.png)出现。从蓝框中随机选一个并点击；此时只记录“已选择移动目标”，不能算已经移动。简单版不识别玩家当前在哪一块。
3. 选中蓝框后可能出现[“小玩意儿”事件卡](images/resonance-pc-deep-dive-simple/09-move-event-item.png)或[“莫测漩涡”事件卡](images/resonance-pc-deep-dive-simple/10-move-event-vortex.png)。卡片出现时必须点击底部“进入”，再处理后续事件，确认结果并返回棋盘；没有卡片时再按实际页面确认移动结果。随后读取右侧目标的任务进度。只有后续界面证实移动已生效，才把它记为成功。
4. 等“旋转”可操作时，进入[旋转选择画面](images/resonance-pc-deep-dive-simple/03-rotate-options.png)，从可用方向中随机选一个。选择方向后还会出现[撤销／确认画面](images/resonance-pc-deep-dive-simple/11-rotate-preview-confirm.png)；必须点击“确认”并验证随后状态，才算真正完成旋转。**成功移动一格，加确认完成一次游戏旋转，算一回合**；两步完成后本地回合计数加一。
5. 等待敌方行动结束。若回到“玩家行动中”，开始下一回合；若出现结算画面，按结束流程处理。重复此循环。

本版只记录**本局尝试并成功完成的移动动作、回合数和事件结果**，不识别当前节点，也不建立节点地图。剩余回合由固定的初始回合额度减去本地已完成回合数得到，不从画面识别。游戏目标的任务进度仍从界面读取，例如右侧“获取灵感”的进度。

只靠移动记录可以避免明显的立即折返，但不能证明整局从未回到某个历史节点。这是简单版的精度边界；不为全局路线去重增加节点识别。

## 重开条件

遇到下列任一情况，停止本局行动并等待结束流程：

- 中途失败，当前局无法继续。
- 根据本地计数，可用回合数耗尽，不再尝试开启新回合。
- 成功过关。

失败和胜利都以进入[结算画面](images/resonance-pc-deep-dive-simple/04-settlement.png)作为一局结束的界面信号。图四的“探索中断”是失败结算示例；出现结算后按画面提示退出，再重新进入关卡。重开时清空本局的移动记录和回合计数。事件处理或进度读取失败时，不把未经确认的结果记为成功；如果无法继续，按失败流程处理。

## 本版不做

- 不做用于观察魔方六面的视角拖动或四角度扫描；图三的一次游戏旋转是每回合必须完成的行动。
- 不识别玩家、Boss或灵感所在格子，不调用相应分类模型。
- 不识别当前节点，不建立完整节点地图、魔方六面坐标或最优路线。

这些是简单版的明确边界，不影响后续另行开发完整识别版。

## 移动与旋转选项的识别办法

以下是对本文件四张示例图做的离线检查，坐标均以游戏**1280×720 客户区**左上角为原点；截图中的 Windows 标题栏不计入坐标。实际操作时优先依据当帧检测结果点击，下面的坐标只是样图测量值。

1. 在玩家行动画面点击右侧“移动”按钮，等待按钮变为青蓝色。只有进入这个选择状态后，才在棋盘区域寻找青蓝色的**格子菱形边框**。框内安全位置作为候选点击点，随机选一个。
2. 玩家在边缘的图二可检出三个候选，中心约为 `(641,363)`、`(855,363)`、`(641,468)`；见[边缘移动候选标注图](images/resonance-pc-deep-dive-simple/05-move-detected.png)。玩家站在边缘时不必先识别其所在格，直接使用游戏给出的蓝框。
3. 完成移动和可能出现的事件后，等右侧“旋转”按钮进入青蓝色可选状态。在棋盘上找青蓝色**箭头头部**，从检测到的方向中随机选一个，不使用格子图标推断旋转方向。
4. 玩家在边缘的图三可检出四个箭头，中心约为 `(742,143)`、`(541,144)`、`(537,236)`、`(746,237)`；见[边缘旋转候选标注图](images/resonance-pc-deep-dive-simple/06-rotate-detected.png)。

新增的玩家在中间的截图也按同一规则检查过：[中间移动候选标注图](images/resonance-pc-deep-dive-simple/07-center-move-detected.png)检出四个蓝框，中心约为 `(535,307)`、`(746,307)`、`(531,413)`、`(750,413)`；[中间旋转候选标注图](images/resonance-pc-deep-dive-simple/08-center-rotate-detected.png)检出四个箭头，中心约为 `(541,142)`、`(742,142)`、`(537,234)`、`(746,235)`。中间和边缘的移动候选数量不同，不能写死为三个或四个。

试验原型先用 HSV 中青蓝色范围提取高亮，再用右侧按钮的高亮状态区分“选择移动”和“选择旋转”：移动阶段筛选面积足够大的菱形边框，旋转阶段筛选面积足够大的箭头头部。选中候选后还要先检查事件卡“进入”或旋转预览“确认”；这些后续界面的判定优先于旧的高亮选择状态。只从对应阶段检出的候选中随机选择；若按钮状态不清、候选数量异常或画面正在过渡，先等待重拍，不按固定坐标盲点。

两种已见事件卡使用同一个底部“进入”入口，离线点击中心约为 `(1090,542)`，见[进入按钮标注图](images/resonance-pc-deep-dive-simple/12-move-enter-detected.png)；卡片标题和图标不同，进入后可能需要不同的事件处理。旋转预览的“确认”中心约为 `(788,542)`，见[旋转确认标注图](images/resonance-pc-deep-dive-simple/13-rotate-confirm-detected.png)。这些坐标仍以客户区为原点；正式运行须先认出入口，再依据当帧位置点击。

在九张静态示例图中，初始画面和结算画面均未输出移动或旋转候选；边缘玩家的移动图输出三个、中间玩家的移动图输出四个，两个旋转图各输出四个箭头；新增的两种卡片均检出“进入”，旋转预览检出“确认”。九张图在亮度为原图80%～120%的模拟变化下，阶段和候选数量不变。这个结果只证明静态截图中的视觉定位可行，**尚未验证这些点在游戏中点击后是否生效**，也未覆盖进入后的事件页面、更多布局和动画时刻。

## 实现时需核对

保持实现简单，但仍需核对这些实际操作入口和结果信号：

- 蓝框和箭头的实机点击区域，以及移动成功、事件结束、旋转完成和敌方阶段结束各自的界面信号。还需用不同布局和边缘位置截图检验候选检测的稳定性。
- 本局固定的初始回合额度、失败与胜利结算的判定，以及退出结算后重新开局的入口。

这些待定项用于下一步核对界面与设计实现；本文件不宣称已有对应的识别和自动操作能力。
