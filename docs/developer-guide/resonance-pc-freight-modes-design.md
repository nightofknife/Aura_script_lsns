# Resonance PC 四种货运模式实现方案

日期：2026-10-04。

状态：四模式货运运行接线已完成，2026-10-04 源码门禁通过并冻结。第 1-8 节保留设计依据，第 9 节保留接口对齐过程，已实施契约和验证以第 10 节为准。规划器和 GUI 由对应线程独立实现；本货运线程未执行游戏任务、打包、推送或发版。

## 1. 已确定的业务规则

一个独立货运任务提供四种互斥模式，共用交易、行车、恢复与到站附加操作。

| 模式 | 目标与固定规则 |
| --- | --- |
| 收益跑商 | 在全部约束内最大化路线预计收益。 |
| 快速跑商 | 有效买卖必须请求砍价/抬价，在书数和单本收益限制内尽量满仓；路线与有限书数分配按最高预计收益选择。 |
| 固定线路跑商 | 严格遵守指定城市顺序，以不超过疲劳上限且尽可能接近上限为目标，允许最后一轮只执行部分航段，最后到达城市清仓。 |
| 指定收益跑商 | 预计收益达到目标后，优先最小化预计疲劳；相同疲劳再优先少用书、少协商、少航段、稳定路径顺序。 |

四种模式均支持路线用书总上限为有限或无限。无限只取消书数约束，单本增量收益下限仍生效。

快速模式的有限书数按整条路线最高收益分配，不按到站顺序先用完。部分城市因阈值、书数限制而未满仓是正常结果。达到满仓后停止加书，不为了替换成更高利润商品继续用书。

客运是独立任务。客运途中交易继续作为客运选项，共享基础城市交易能力；货运模式不自动改变客运交易规则。

当前规划输出包含 `buys[*].quantity`，但执行主要接受商品名称、书数和协商标志。满仓指标首先是计划值，不冒充实测货舱数量。执行时必须检查目标商品是否完整选中、用书是否完成及购买是否确认。

当前买货存在部分漏选仍继续、未确认购买仍返回 `success=True` 的路径。它们应在执行结果契约整理时收紧，并单独验证客运共享调用方。

## 3. 统一参数契约

以下字段为拟定的新契约；字段名和 JSON/YAML schema 在编码时统一落地。现有 `book_budget` 继续作为唯一的路线用书总上限字段。

| 字段 | 语义 |
| --- | --- |
| `trade_mode` | `profit / quick / fixed / target`，默认 `profit`。 |
| `fatigue_budget` | 路线预计疲劳硬上限，包含行车和计划协商。 |
| `cargo_capacity` | 每段货舱容量。 |
| `book_budget` | 非负整数为全路线总上限；`null` 明确表示无限；`0` 表示不用书。不能以巨大整数伪装无限。 |
| `book_profit_threshold` | 每新增一本书的预计增量收益下限，默认 500000；四模式都生效。 |
| `book_policy` | `profit / fill`：允许继续优化满舱内的商品构成，或到首次最大装载量即停止加书。快速模式固定为 `fill`。 |
| `negotiation_policy` | `auto / required / disabled`。快速模式固定为 `required`。 |
| `available_city_ids` | 非固定模式的候选城市集合。 |
| `required_end_city_ids` | 非固定模式允许的终点集合；空缺表示自动选择。 |
| `fixed_route_city_ids` | 固定模式的完整有序城市列表，包含起点和终点，允许非相邻重复城市。 |
| `reposition_to_route` | 固定线路“自动前往起点”开关，默认关闭；当前城市不符且未开启时提示并停止。 |
| `target_profit` | 指定收益模式的正数目标；其他模式不参与计算。 |
| 声望、解锁、协商成功率与幅度 | 四模式共用的账号模型数据。 |
| 协商尝试次数、到站等待、疲劳药 | 四模式共用的执行设置。 |
| 喝水、便当、恢复下限、便当优先级 | 四模式共用的恢复设置。 |
| 投资、倒垃圾、拣货 | 四模式共用的附加操作设置。 |

内部使用结构化请求分组：规划约束、模式专属配置、执行配置、恢复配置、附加操作配置。YAML/action 边界仍使用框架可序列化字段，由单个适配器生成请求，避免每层复制一套校验。

`auto_book` 不再同时承担自动数量、无限预算和收益策略三种职责。新契约由 `book_budget` 和 `book_policy` 表达，不增加旧字段迁移或兼容别名。GUI 保存无关模式配置供切换恢复，但当前运行只生成该模式的有效参数。

“不用书”可在 GUI 保留为快捷选择，运行输入为 `book_budget=0`；“限量/无限”是数量限制，“按收益/尽量满仓”是策略，不再将它们做成互相混淆的四个选项。

`trade_level`、`active_events` 当前不影响精确规划。新货运参数区不再将它们展示为有效调节项，数据模型暂不扩展活动、现金预算或船员效果。

## 4. 共同候选与用书规则

### 4.1 冻结输入

每次正式规划固定当前城市、行情快照、移动疲劳、进货量、声望/税率、商品解锁、账号协商参数和全部有效模式参数。共同模型沿用现有游戏取整规则和 `Fraction` 疲劳，不以浮点近似改变预算边界。

预览允许指定起点；正式运行识别实际所在城市。用户已确认：固定线路起点不符时，提供可选的自动前往起点功能；未开启则提示并停止，开启则先前往线路起点，已经在起点则跳过。

实现安排：定位行程只导航，不买卖、不用书、不协商，不属于贸易循环。定位行程疲劳计入整个任务的疲劳上限；出发前统一检查定位行程和选定的全部航段，预览分别展示定位疲劳、线路疲劳和总疲劳。

### 4.2 一本书的收益

对同一城市边、同一协商配置、同一货舱及账号条件，令 `P(k)` 为使用 k 本书时的预计收益，`Q(k)` 为计划装载量。

```text
第 k 本书增量收益 = P(k) - P(k - 1)
允许新增第 k 本书：增量收益 > 0 且增量收益 >= book_profit_threshold
```

建议统一采用“达到下限即可”，并单独覆盖等于 500000 的边界。当前 Auto Book 用 `>`，手动模式用 `>=`，这属于需要明确记录并测试的规则变更。

不能用 `P(k)/k`、路线平均书收益或其他站的收益弥补不达标的一本。允许 k 本的候选，要求其前 k 本都达标。

只纳入共同商品模型中的可购盈利商品；不为填空位自动买入负利润商品。

### 4.3 无限书数仍有有限搜索边界

`profit` 策略的内部最大候选书数由利润饱和点、收益阈值和货舱推导；`fill` 策略由首次达到最大装载量的书数与收益阈值推导。阈值为 0 时仍禁止零增量用书。

大书数场景采用累计数量/收益曲线、精确断点或经证明等价的计算边界。不能用任意 99/999 本上限截断，也不能用 Beam、Top-K 或抽样代替精确结果。

收益和指定收益模式在无限书数下仍可能需要低书数候选。直接只保留每段最大利润候选，会破坏指定收益模式“达标后少用书”的平局规则。

### 4.4 有限书数全局分配

所有候选保留 `books_used`，路线累计不得超过 `book_budget`。由全路线搜索共同决定城市、商品、协商和书数，不先逐城分书再选路线，也不按单本收益排序做局部贪心。

快速模式同样保留达到满仓之前的合法书数候选。在总书数不足时，以整条路线最高预计收益分配；不能过滤掉部分装载方案导致本来可运行的路线无解。

### 4.5 协商与空载段

`auto` 允许四种协商组合，`required` 在有效交易候选中只允许双协商，`disabled` 只允许不协商。

空载迁移是明确的导航段，不发生虚构买卖或协商。普通、目标收益、固定线路可使用合法导航段；快速模式的贸易段必须有有效购买，必要起点/终点连接若保留空载迁移，应在预览单独标示而不是当作满仓贸易段。

规划仍使用满 20% 定价和原协商期望疲劳。用户已确认：达到最大尝试次数仍未满 20% 时，按照当前价格成交并记录降级结果。快速模式“必须进行”是必须发起协商，不新增无限重试。页面异常、操作失败、交易未确认仍应中止。

## 5. 三类精确规划器承载四模式

### 5.1 收益跑商与快速跑商

两模式共享最大利润搜索。快速模式在候选层固定 `fill + required`，书预算与收益阈值继续生效。

最终排序为：最大预计收益、最小预计疲劳、最少书数、最少完整协商次数、最少航段、稳定路径顺序。沿用可证明等价的 dense/sparse 后端及整数疲劳 tick。

### 5.2 固定线路跑商

采用线路位置推进的精确动态规划。状态以线路下标代替自由城市选择，并保留书数、疲劳和协商/收益标签；沿相邻指定城市构造共同交易候选。用户确认的首要目标是最大化不超过上限的预计疲劳，不能继续按最高收益选择结束位置。相同疲劳时，设计上沿用收益优先，再少用书、少协商、少航段和稳定路径顺序的平局规则。

不直接调用旧固定循环搜索，因为它会选择线路，不等同于遵守用户指定顺序。

用户已确认取消指定执行次数。首尾相同的闭环沿指定顺序持续循环，直到规划选出的疲劳最接近上限的合法结束位置；允许最后一轮只执行部分航段，不要求回到循环起点。总书数、单本收益下限和疲劳限制仍覆盖整个计划。开放线路只能沿已给定的航段推进，不擅自追加返程或循环连接。

行车和协商消耗离散，不能保证恰好等于上限。用户已确认采用“不超过上限，尽可能接近并清仓”：搜索所有合法线路前缀及交易候选后选择最接近的预计疲劳，不为凑满预算改变城市顺序、超限或添加虚构协商。不能仅逐段贪心推进，因为不同协商候选会影响最终可达的疲劳。

出发前统一规划并校验选定前缀，预算不足完成一整圈不再构成失败；无法执行任何合法贸易航段时返回 `fixed_route_infeasible`。跨轮边界城市只出现一个逻辑到站节点：先卖上一轮货再买下一轮货，不重复空清仓。最终节点只卖不买，最后清仓和便当只执行一次。

循环搜索的有限边界由疲劳预算和正消耗航段推导，不设置任意执行次数上限；零消耗循环必须显式检测，避免无界展开。预检继续依据原协商期望疲劳，不承诺实机随机消耗恰好耗满或永不超限；保留实际完成整圈数、最后部分轮次、航段及失败位置。

### 5.3 指定收益跑商

在全部约束内寻找 `P >= target_profit` 的方案，排序为：最小预计疲劳、最少书数、最少完整协商次数、最少航段、稳定路径顺序。不要求把疲劳预算用完，不为追求更高超额利润多耗疲劳。

初版实现独立的精确稀疏目标搜索，共享候选和 fatigue tick。按疲劳层递增处理，在完整处理最早达标且终点合法的疲劳层后选出最优结果。达到收益但终点不符合约束时不能提前停止。

现有最大利润搜索的状态合并、Fenwick 支配和终态分数不能直接改一个比较符复用。必须保留对目标可达性和少书/少协商/少航段有意义的非支配标签；少利润但更短的路径在尚未达标时也可能有价值。

收益可在搜索可达性维度上精确截到目标，但必须保留真实累计收益用于输出和增量计算。任何剪枝均需要证明保持完整排序，并通过小图暴力枚举验证。

全预算范围内不可达时返回 `target_unreachable`，给出同约束下最高预计收益作为诊断；不执行诊断路线。必要时调用共同最大利润搜索取得该值，不能把未验证上界冒充可达收益。

此目标不建立“1 元收益一个数组格”的巨大 dense 维度；后续优化以性能测量为依据。

## 6. 共同执行、恢复和结果

### 6.1 内部模块划分建议

| 拟提取能力 | 职责 |
| --- | --- |
| 货运请求/路线类型 | 统一模式请求、约束、城市访问、贸易段和结果。 |
| 市场与规则输入准备 | 数据读取、标准化、快照及城市解析，保留服务缓存生命周期。 |
| 边候选与用书策略 | 商品定价、税率、数量、收益增量、装载量、协商过滤。 |
| 模式规划器 | 最大利润、固定序列、目标收益的精确搜索。 |
| 共享城市交易 | 页面导航、用书、选货、协商、结算及业务确认；供货运和客运使用。 |
| 货运路线执行 | 城市访问索引、单段交易、行车、到站处理及阻塞。 |
| 到站附加操作 | 投资、回收、指定节点喝水，显式接收/返回页面状态。 |
| 运行状态与进度 | 统一完成、跳过、失败、取消及部分执行明细。 |
| 完整货运任务 | 准备、规划、执行、终点清仓、便当子任务及最终结果。 |

只有确有共享状态/缓存的能力使用 service；纯计算和内部执行 helper 不为拆文件而全部注册新 action。

### 6.2 完整执行顺序

```text
独立货运任务
  -> 参数校验与必要开跑读取
  -> 确认当前城市、冻结行情、调用模式规划器
  -> 校验整条执行计划（包含固定线路可选的定位行程）
  -> 固定线路按开关自动前往起点；起点不符且关闭开关则提示停止
  -> 起点卖已有货物、按计划用书/选货/砍价/买货
  -> 行车并确认到达
  -> 现有投资/回收/指定节点喝水
  -> 中间城市卖上一段货、买下一段货
  -> 终点最后一次抬价与清仓，确认主界面
  -> 按开关调用现有便当任务
  -> 合并结果并报告完整货运完成
```

路线边的 `raise_to_cap` 指目标城市卖该段货物时的抬价，不是出发城市卖上一段货。规划转执行时生成显式城市访问对象：当前访问的卖货意图来自前一段，买货意图来自后一段。末站只卖不买。重复城市和轮次按访问索引区分。

用户已确认：首站出售已有货物不抬价，快速模式也不例外。该清仓不计入规划路线盈利或指定收益目标；后续出售本次路线购入的货物，按前一段的抬价标志执行。

公共业务结果需要区分计划值和确认值：计划书数/实际确认用书、计划装载/商品是否完整选中、请求协商/实际是否到顶、计划收益/结算确认。不新增未经请求的货舱 OCR 或现金预算校验。

所有同步操作沿现有框架取消/worker 规则运行；遇到部分消费或交易失败保留明细，不能自动重试整份路线或整批便当。提取模块时验证既有 `asyncio.to_thread` 与注册子任务路径的取消边界，不附带改造整个框架。

### 6.3 恢复边界

喝水仍在最后一个允许喝水的实际到站节点；便当仍在全部货运交易结束后处理。48 点缓冲不加入预算计算，恢复量不扩充路线疲劳预算，不增加更早/更多恢复城市。

喝水的后续消耗简易估算与求解器的协商期望疲劳保持不同用途。四模式都根据实际生成的路线标志计算尚未执行的操作，不因快速模式额外重复计数。

便当按当前 `bento_consumption_pc.yaml` 的消费能力调用，不恢复旧文档里的本地清单流程或新增中途盘点。模式改造不同时变更已经修复的便当界面等待、返回顶部和评分操作。

### 6.4 结果与缓存

统一返回模式、参数快照、行情标识、实际起终点、城市访问和路线、预计收益/疲劳、书总量和上限、每段装载量、停止加书原因、协商意图、规划状态、执行状态与恢复明细。

指定收益增加 `target_profit / target_reached / target_gap`；固定线路增加完成整圈数、最后部分轮次、结束线路位置和预计剩余疲劳预算，不接收执行次数限制。`target_reached` 指规划预测，不能冒充实测累计收益达标。

每段未满仓原因至少区分：总书数限制、收益阈值、无合适商品、无需用书已满仓。有限书预算可标示“为其他路段保留书数”，不能误报为该段收益不足。

规划状态：`ok / no_plan / target_unreachable / fixed_route_infeasible`；非法输入单独报校验错误。执行状态保持完成、受阻、失败、取消、正常跳过的业务区分。

缓存键包含模式、书数有限/无限、用书/协商策略、目标收益、完整固定线路、自动前往起点开关、实际出发城市和所有共同模型输入；不混入便当/喝水等不改变规划的开关。读取时保留现有深拷贝隔离。

| 固定线路可跑多圈但最后一圈预算不足 | 执行完整圈和最接近上限的合法部分圈，全部轮次共享书预算。 |

| 固定线路较高收益前缀消耗更少、另一合法前缀更接近上限 | 优先选择更接近疲劳上限的前缀，不能沿用最高收益终态排序。 |
| 固定线路计划恰好达到疲劳/书数上限 | 允许执行；实机异常仍正常受阻或取消。 |
| 固定线路起点不符、自动前往起点关闭 | 提示并停止，不出发、不交易。 |
| 固定线路起点不符、自动前往起点开启 | 全部计划通过预检后先导航至起点；定位行程不交易、不属于贸易循环，疲劳计入总上限。 |
| 首站已有货物、快速模式开启 | 清仓不抬价；之后出售本次路线买入的货物按计划抬价。 |
| 协商达到尝试次数仍未满 20% | 按当前价格成交，不无限重试。 |
| 目标 1000 万：路线 A 利润 1200 万/疲劳 600，B 利润 1000 万/疲劳 400 | 指定收益选 B，收益模式按最高利润选择。 |
| 目标两路线疲劳相同，较低利润路线少用书或少跑站且仍达标 | 指定收益保留并选择资源更省的路线，不被最大利润标签错误剪掉。 |
| 目标达标但指定终点未到 | 继续规划至合法终点；无解则不可达。 |
| 目标在书数/阈值/疲劳限制下不可达 | 给诊断而不自动执行未达标路线。 |
| 部分商品漏选、用书未完成、购买未确认 | 不报告交易成功，不继续盲目发车。 |
| 降级协商、恢复关闭/开启、阻塞、取消、部分便当消费 | 结果保留实际明细，完整任务不提前完成或重复消费。 |

### 9.3 校验责任与模式归一化

GUI 负责控件范围、必填提示、精确单位转换和过滤当前模式不适用字段。货运入口拥有权威校验，在任何消费、清仓或发车前生成统一请求；试算和正式执行调用同一校验/归一化能力。GUI 提示不能替代 CLI、YAML 或其他任务调用的业务校验。

货运入口检查模式、整数/金额、城市目录、必要字段、排序、恢复配置、执行配置及当前城市识别；快速规则由后端派生，不能因 GUI 传入 disabled 而回退。规划层验证图数据、边可达性、全路线书数和疲劳、单本阈值、指定收益可达性及精确搜索边界。执行层确认界面、选货、用书、成交、到达及最终收尾。账号/市场读取异常归属准备阶段，不冒充无解。

固定模式忽略非固定选城/终点和收益目标，不设置次数；目标模式必须有正目标。预览 start city 在固定模式下也适用定位开关。正式运行重新识别实际城市、刷新必要数据并规划，不直接执行旧预览，不增加途中纠正路线或预算拒绝机制。

| 请求与阶段 | `trade_mode`、`request_kind=preview/run`、`input_snapshot`、`snapshot_id`、`planning_status`、`status`、`success`、`reason`、结构化 `error={code,message,detail}`。 |
| 规划状态 | `ok / no_plan / target_unreachable / fixed_route_infeasible`；校验/数据错误另用 error，不塞入“无解”。 |
| 运行状态 | `planned / completed / stopped / blocked / failed / cancelled`；试算成功为 planned，不冒充执行 completed。 |
| 路线 | `route` 是实际选定前缀的贸易/导航段；`city_visits` 是按访问序号区分的城市节点，包含 `city_index / city_id / city_name / role / phases`，不能按城市 ID 合并重复访问。 |
| 定位 | `reposition={required,route,expected_fatigue,expected_fatigue_exact}`，与贸易 route 分离；总预计疲劳包含定位，不重复相加；关闭且不在起点输出起点不符原因。 |
| 计划资源 | 每段 `books_used / buys / loaded_quantity / cargo_capacity / is_full_load / load_ratio / bargain_to_cap / raise_to_cap / book_stop_reason`；满仓和收益均为计划值，不能标成实测。装载命名采用规划器当前工作稿，待接口对齐后再固化。 |
| 指定收益 | `target_profit / target_reached / target_gap`、同约束可达最高收益诊断；不可达诊断不得混入可执行 route。 |
| 固定线路 | `completed_circuits / partial_circuit_legs / partial_circuit_city_path_ids / termination_route_position / termination_city_id / stop_reason` 与预计预算余量；使用规划器当前工作稿命名，不接收或输出作为限制的执行次数。 |
| 执行明细 | `execution / final_sale / initial_city / page_state / blocked_at / blocked_leg`，保留部分完成、不完整选货、消费和协商降级证据；首站清理不抬价且不计计划利润。 |
| 恢复明细 | `sparkling_water_plan / sparkling_water / bento_consumption / fatigue_medicine_used / fatigue_medicine_use_count`；计划、跳过、已确认消费和失败分开。 |

拟提供稳定原因类别：`no_profitable_route / insufficient_fatigue_budget / required_end_unreachable / target_unreachable / fixed_start_mismatch / fixed_route_infeasible / unsupported_city / invalid_input / preparation_failed / transaction_not_confirmed / arrival_not_confirmed / cancelled`。规划器内部细分码由货运适配器映射并保留原始 detail；GUI 可展示未知细分码的 message，不按中文文本匹配行为。

`target_reached` 始终是预计达标，不代表实际现金收益。实际疲劳未读取或实际金额未确认时输出 null/未知，不能用计划收益、操作成功或未经读取的零值填充实测栏。便当任务保持基础恢复量规则，不新增实际恢复量 OCR。

`success=true` 的执行完成必须包含最后清仓业务确认和启用的便当任务收尾；规划不可达、起点不符或消费失败不得因节点运行成功报告货运完成。取消/阻塞不重试整条路线，保留已经确认的资源消耗。

### 9.5 城市阶段与进度事件

沿用当前事件名 `task.resonance_pc_trade_progress` 和 `schema=resonance_pc.trade_progress.v1`，在不改变既有 stage/index 语义的前提下补充模式、定位、资源和显式阶段计划；不建立另一套日志推断通道。具体字段双方对齐后同时修改生产者和 GUI 消费者。

| 事件字段 | 契约 |
| --- | --- |
| `cid / sequence` | 同一次完整货运的相关 ID 与严格递增整数序号；便当 child task 沿用父任务关联和序号，GUI 忽略其他运行及旧事件。 |
| `stage / state` | stage 表示业务阶段；state 为 `started / progress / completed / skipped / blocked / failed / cancelled`。事件 completed 只确认当前阶段。 |
| `trade_mode / request_kind` | 区分四模式和试算/运行，试算不产生交易或恢复动作完成事件。 |
| `city_index / city_count` | 贸易城市访问从 0 开始，count 为总节点数；始发为 0、末站为最后节点；不按城市 ID 定位。定位事件无贸易 city_index，不挤占贸易节点。 |
| `leg_index / leg_count` | 贸易 route 航段从 0 开始；travel 对应出发节点，arrival 对应到达节点。定位进度在 data.reposition 内独立计数。 |
| 城市标识 | 保留 `current_city / from_city / to_city` 名称，补充城市 ID；展示不用名称反解 ID。 |
| `operation / data` | negotiation 的 operation 为 bargain/raise；data 承载计划摘要、确认结果、跳过原因、错误及资源快照。 |
| `data.resources` | 累计确认用书、累计确认协商疲劳、基础恢复量及最近真实读取疲劳；未知值 null。累计值是快照，GUI 不能逐事件相加以免重放重复计数。 |
| `data.progress` | 运行阶段确定后提供 `completed_units / total_units`；规划搜索可只提供忙碌状态/搜索统计，不编造确定百分比或完成时间。 |

准备 stage 使用现有 `target / city / market / planning`，增加独立 `reposition`；贸易 stage 保留现有 `leg / sell / buy / negotiation / travel / arrival / investment / rubbish_recycling / final_sale / bento / sparkling_water`，拟补充 `city_trade / books` 的显式业务阶段，终态使用 `task`。GUI 对未知 stage 可以展示基础状态，不改变货运执行。

planning completed 携带 `data.route / data.summary / data.city_visits` 和独立定位计划。货运生成每个访问的 phases 及适用性：首站清仓不抬价，中间站卖后买，末站只清仓；不适用阶段显式 skipped。GUI 展示货运提供的阶段，不自行推断投资/汽水是否可用或自行生成便当计划。

城市阶段计划拟统一为 `phase={key,status,reason}`，key 使用上述业务 stage；首次规划给出 waiting/skipped，运行事件再更新。同城市重复出现依访问序号区分。可选恢复未启用、无可用资源或下限阻止恢复时输出 skipped 原因，不用静默消失掩盖失败。

整体任务进度至少包含准备、定位（如需）、每次城市交易/行车/到站、最后清仓和便当收尾；路线行车完成不等于整体 100%。便当待执行时不发布 task completed；blocked/failed/cancelled 保留最后进度，不把后续未执行阶段改为成功。

### 9.6 对齐与验收清单

固化接口前由 GUI 线程确认：700/750/投资 true 的默认基线、金额“万”的输入精度、用书界面状态映射、城市阶段和资源字段展示需求。由本线程与规划器线程核对新 service 签名和装载/固定圈数/定位输出字段，不同时编辑求解器。未对齐的新字段保持草案，不让两边各自发明正式 schema。

当前规划器工作稿已有 `trade_mode / book_policy / negotiation_policy / fixed_route_city_ids / reposition_to_route / target_profit` 服务参数；定位输出暂为 `reposition_route / reposition_expected_fatigue / route_expected_fatigue` 及其 exact 值。本节的分组 reposition 和 city_visits 属货运适配层提案，不要求 GUI 直接依赖尚在修改的求解器字典，也不要求规划器为展示重写内部结构。`recovery_snapshot` 由货运准备能力生成/验证，保留给内部任务编排，不作为用户手填参数或用旧缓存绕过必要刷新。

实施验收覆盖：试算/运行共同参数一致；无限 null 穿过 GUI/IPC/YAML/action 不变 0；开关切换保留有限数值但不忽略总预算；阈值 50 万精确转换；所有默认值同源；固定起点不符开关开/关；重复城市及末轮清仓；计划值不冒充实测；便当结束前任务不完成；取消/部分消费不重复计数。当前只更新方案文档，不以此宣称运行或实机验证通过。

### 10.1 恢复 Preflight 责任

正式 `auto_cycle_trade_flow` 当前不自行执行整套玩家数据 preflight。GUI 在启用汽水/便当时应保留一次隐含玩家数据刷新，并把本次刷新的 `recovery_snapshot` 传入完整货运任务；不增加可见“数据采集”工作流任务。汽水开启时，货运入口必须验证 snapshot 的持久化、疲劳和汽水次数字段，缺失/不合法在开跑前拒绝，不能用陈旧缓存补齐。
