# PC 便当消费子任务与父任务边界

状态：已按用户最新要求收紧为明确清单执行接口。调用说明见 [吃便当子任务](resonance-pc-bento-consumption.md)。
规划业务规则仍在 [到站恢复方案](resonance-pc-arrival-recovery-design.md)，但这些规则由跑商等父任务执行，不属于吃便当子任务。

## 1. 父任务负责什么

- 沿用现有开跑前的一次读取任务保存便当库存，消费规划读取本地数据，不增加重复刷新；需要当前疲劳时单独读取疲劳。
- 处理用户设置的恢复下限、资源优先级、临期排序，计算吃哪些、吃几份。
- 气泡水最后站点和后续消耗由父任务估算；协商简易公式只用于恢复时机/喝水量，不改变原有跑商疲劳算法和求解器。48点暂不参与计算、不扣预算。
- 放不下的临期便当跳过，在能完整使用的候选中临期优先；这些决策不放入消费子任务。
- 把明确的便当身份按消费顺序整理为 `meals` 清单。
- 确认已回主界面后调用子任务，检查业务返回，必要时另行读取消费后疲劳。
- 用户自行负责预算可行性，不额外增加预算纠正、绕路或提前恢复。

## 2. 子任务只负责什么

- 唯一业务输入 `meals`，每条一份，不接收开始疲劳、恢复下限、优先级或最大份数。
- 从本地缓存核对清单，不重新盘点；缓存不满足要求时失败，不自动刷新。
- 从主界面开始，严格按清单顺序定位指定目标、单份使用、确认效果、评分、回柜并在本地记账。
- 正常完成后点击火车图标回主界面。
- 找不到指定目标或操作失败时停止并报告，不换其他菜品，不跳过指定目标后继续吃其他份。
- 不读取疲劳或实际恢复量，不自主减少/增加清单，不把旧参数翻译成新参数。

任务：`tasks:bento_consumption_pc.yaml:bento_consumption_pc`。
公开Action：`resonance_pc.consume_bentos`。
父任务YAML通过 `aura.run_task` 调用，Python工作流可复用同一Action，不构造新runner或复制UI逻辑。
不加入“小任务”GUI，不创建独立设置页。

## 3. 清单身份

工作餐：`kind=work_meals` 与 `issue_time=05:00/12:00/18:00`。
爱心便当：`kind=love_bentos` 与 `role_id/food_id/remaining_days`。
这些字段对应现有读取结果；名称、评分和恢复量不允许调用方覆盖。

每条一份，同一身份重复请求拒绝；空列表从主界面直接返回无操作。
第一次使用前只在本地数据中核对整份清单是否存在。消费期间指定目标无法定位或页面匹配不确定，停止并保留已经完成部分，不自动替换或启动全量扫描。
剩余天数在子任务中只是精确身份的一部分，不用于自行重排。

## 4. 单份UI流程

```text
读取本地库存并核对清单 -> 主界面 -> 个人信息 -> 疲劳恢复页 -> 便当柜
-> 定位指定条目 -> 单份使用 -> 确认（若出现）
-> 食用效果 -> 点击空白
   工作餐：回便当柜，本地对应槽位已标记使用
   爱心便当：选星级 -> 确定 -> 回便当柜，本地对应条目已扣除
-> 下一条或点击火车图标返回主界面
```

只点单份“使用”，不点“全部使用”，不勾选“今日不再提示”。
工作餐蓝色使用可用，灰白使用禁用，未到发放时间没有单份使用按钮；不能用“全部使用”判断可用性。
爱心便当卡片每次重新定位，不依赖旧滚动坐标。效果确认与评分完成分离，不因评分失败而重新消费。
定位只比较清单指定的菜品、角色和天数模板；优先检查当前视口，找不到才回顶向下找，找到即停止。禁止以 `LoveBentoScanner.read/read_page/read_frame/classify` 重新建立库存。

## 5. 评分和记账

- 83300002菜肉俱全汉堡、83300011焦香水果派：一星。
- 其余九种已知菜品：五星。
- 按菜品ID判断，不按颜色或赠送角色判断。
- 基础恢复量只用于返回和记录：工作餐36，爱心便当FoodFactory基础值；不做账号加成或现场恢复量读取。

持久化复用 `core/persistent_data`，只更新便当库存与本功能消费记录，保留其他字段。
已确认消费及时记录，即使随后取消也不能丢弃证据。未完成评分不能撤销已经消费的记录。
子任务不更新疲劳值；父任务应刷新而非重复使用消费前疲劳缓存。

## 6. 后续跑商接入（本次不做）

具体接入设计见 [货运气泡水与便当接入设计](resonance-pc-freight-recovery-integration.md)，不改变本文的消费子任务职责。

在最终交易结束后，由跑商负责读取疲劳、计算便当清单、确认返回主界面，再调用子任务。
只在货运收尾吃，不延后到整个组合结束；货运先于客运时，完成货运恢复后继续原客运流程。不增加客运恢复逻辑，不修改客运参数、规划和预算。
组合客货运直接调用共享跑商Action，因此不能只在单独跑商YAML末尾接入；后续应统一在共享flow中接一次，避免遗漏或重复。
不修改当前气泡水或协商求解器。未来的其他大任务同样自己规划清单，再调用此消费子任务。

## 7. 验证重点

- 仅 `meals` 一个业务参数，禁止旧规划参数；未给清单不能启动消费。
- 清单顺序不被工作餐优先或临期排序改变；清单外资源不消费。
- 指定目标缺失时不换餐，整份初始清单缺失时不先消费前面条目。
- 本地数据缺失/需要刷新时不点击、不自动重扫；消费前后均不盘点。
- 不访问疲劳读取或恢复量OCR，不因疲劳不足以满足旧下限而跳过明确请求。
- 单份消费、1星/5星、灰白/缺失按钮、重复记账、部分失败、取消和返回主界面。
- 初始主界面校验与正常返回；其他页面启动无点击。
- 模板fixture、任务manifest与离线回归；实机验证另经用户授权。
