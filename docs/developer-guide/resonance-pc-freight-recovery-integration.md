# PC 货运气泡水与便当恢复

当前规则：在货运起点、每个到站城市、城市交易后准备出发以及最终交易结束的安全节点检查疲劳。交易结束时顺手读取买卖页面顶部的疲劳；普通行车确认到站后，将该路段已知疲劳加到最近基准上。只有没有可靠基准、识别失败或路途中发生无法准确计算的特殊情况时，才专门打开个人信息页兜底读取，不再每个节点都打开个人信息页。气泡水和便当分别设置开始线、停止线；固定先处理气泡水，再用喝水后的最新实际疲劳判断便当。便当内部按用户设置的 `bento_priority` 选择工作餐与爱心便当。

本次修改只调整恢复触发和停止条件。路线、利润、协商策略及原疲劳预算保持原口径；恢复量不回补路线预算，不因后续预计消耗提前喝水或吃便当。

## 参数与校验

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `auto_sparkling_water` | false | 自动喝气泡水开关 |
| `sparkling_water_start_threshold` | 600 | 气泡水开始线 |
| `sparkling_water_stop_threshold` | 100 | 气泡水停止线 |
| `auto_bento` | false | 自动吃便当开关 |
| `bento_start_threshold` | 600 | 便当开始线 |
| `bento_stop_threshold` | 100 | 便当停止线 |
| `bento_priority` | `[work_meals, love_bentos]` | 使用便当类型及顺序 |

四条线默认分别为 600、100、600、100，用户可以修改。启用某项自动恢复时，该项两条线必须都是整数，且满足 `start > stop >= 0`。GUI 和后端都校验；没有填写完整时在操作游戏前拒绝执行。关闭某项自动恢复时不要求填写该项两条线。

原 `base_fatigue_reserve`、固定恢复目标 `target_recovery_amount` 和 `allow_exceed_target` 不再控制自动恢复，不把旧值迁移成新阈值。

气泡水与便当的顺序固定为先水后便当，不新增恢复方式顺序参数。`bento_priority` 仅控制工作餐与爱心便当的先后；关闭某项或气泡水不可用时正常跳过，仍判断便当条件。

任务 `auto_cycle_trade_pc` 将四阈值及便当类型顺序直接传给共享 `resonance_pc.auto_cycle_trade_flow`；组合任务的 `trade_inputs` 保留相同字段 schema。纯客运与试算输入不增加这些字段。组合客货运的 `combined_auto_bento_unsupported` 限制保持，尚未扩展客运或组合便当执行。

## 城市检查顺序

交易所页面顶部的 `当前疲劳/上限` 是新的现场读数入口。城市交易完成后，等待最后结算弹窗关闭、页面稳定，在退出交易所前读取；同城先卖后买时采用最后一次买入后的读数，只卖不买时采用卖出后的读数。这个读数已经包含本次砍价、抬价等消耗，不能再叠加本次协商次数。读取失败不得沿用交易前的旧读数。

跑商前的个人页、交易页和便当柜统一调用 `_fatigue_observation.py`。每轮只截图一次，按亮白字形的连通域和窄单笔分隔笔画动态确定两侧边界，再分别 OCR 当前疲劳与上限；中间分隔符不送入 OCR，不把数字 `1` 替换为 `/`。分区随数字位数变化，不按包围区域中点硬切。便当柜包围区域左扩至 `(1139,20,132,40)`，容纳两侧四位数。无法唯一分区或字形触及区域边缘时，本轮视为未知。

两侧必须分别是完整纯数字且置信度均不低于 0.9，上限大于零；允许当前疲劳超过名义上限。只有连续两张新截图得到相同的 `(当前疲劳, 上限)` 才接受，中间任何失败或数值变化都会打断一致确认，同一帧反复 OCR 不累计次数。个人页、交易页分别保留三秒预算，便当柜沿用布局中的五秒局部预算及消费任务总预算；超时和取消均不能提交本轮值。交易页失败走个人页兜底，个人页或便当柜失败则停止，不保存或返回消费前旧值充当当前疲劳。

途中使用独立疲劳账本：

```text
到站疲劳 = 最近一次现场读数 + 此后已确认普通行车路段的疲劳消耗之和
```

同城重复检查且没有新增消耗时复用有效读数。普通行车只有确认成功到站、路段疲劳为严格非负整数时才累计；不把计划中尚未完成的路段加入。行车期间公开当前疲劳为空，避免将出发前的读数当作到站结果。没有发生交易的站点继续沿用账本；交易页面的新读数以及喝水、便当、兜底个人信息页的新读数都会重置基准并清零路途累计。

使用疲劳药、实际拖车出发、遭遇操作、未知行车方式、缺失路段消耗或到站未确认时，账本失效。确认安全到站后再兜底现场读取，未到站时不授权恢复。拖车仅尝试后被拒绝、最终仍正常行车的情况不按实际使用拖车处理。疲劳上限仅作为读取信息保留；游戏允许超过上限的疲劳，不截断该读数。

```text
确认货运起点、到站、交易后出发前或最终交易后的安全城市页面
  -> 有交易页面现场读数或可靠的已确认路途累计值：直接使用
     否则：通过个人信息页读取当前实际疲劳建立基准
  -> 启用气泡水且最新 F > water_start：
       城市有休息区且有有效免费次数时，按 water_stop 计算杯数并执行
       没有休息区或免费次数为零则正常跳过
  -> 获得喝水后的实际疲劳并更新基准
  -> 用最新 F 重新判断便当，不能沿用喝水前的触发结果：
       启用且 F > bento_start 时调用完整便当子任务
       按 bento_priority 选择便当类型，每份完成后现场读取疲劳
       实际疲劳 <= bento_stop 或无可用餐时停止
  -> 确认回到预期城市页面，继续交易或下一段行车
```

开始条件是严格大于。实际疲劳等于开始线时不触发，不能根据后续行车、协商或缓存预计疲劳提前恢复。某项已经触发后以该项停止线结束，不因降到开始线以下就提前停止。

每个城市抵达分别检查，相同城市的不同到达可以再次触发；本地交易或协商结束后，按交易页最新读数检查，防止城市操作期间刚刚超过开始线。同城市的检查点在进度中分别更新，不因上一次跳过或完成而跳过下一次检查。终点到站和最终交易后也只按各自开始条件判断，YAML 不追加无条件便当节点。受阻、到站失败、取消或未知页面不授权恢复输入。

例如默认两项开始线都是 600、停止线都是 100：到站疲劳 650，当前有 6 杯免费水时，先喝到实测 350，便当不再满足开始线而跳过；到站疲劳 950，同样喝 6 杯后实测 650，便当仍超过 600，才按用户的便当类型优先级逐份吃到 100 或以下。当前城市不能喝水时，直接用当前有效疲劳判断便当。不能在进入城市时预先把两项都排成必执行。

气泡水不可用时仍可按便当自己的条件使用便当；次数或页面状态不明属于失败，不伪装成免费次数为零。

## 气泡水用量

气泡水沿用每杯恢复 50 的规则，只用有效剩余免费次数，不购买次数、不绕路。设当前有效疲劳（现场读数或已确认路途累计）为 F、停止线为 S、剩余免费次数为 N，触发后所需杯数为：

```text
needed = ceil((F - S) / 50)
K = min(N, needed, (F - 1) // 50)
```

最后一杯允许使疲劳跨过停止线，但每杯后疲劳仍须大于 0。停止线为 0 也保留此保护；免费次数不足或无法再喝一杯时正常停止。杯数不计入剩余行车/协商消耗，不使用预计终点疲劳约束。

例如开始线 600、停止线 370、现场疲劳 621、免费次数为 6 时计划 6 杯，固定每杯 50 的预计结果为 321；免费次数只有 4 时只喝 4 杯。现场疲劳 600 不触发。此处预计值只说明杯数，不替代恢复后的实测疲劳。

逐杯确认、免费次数记账、`requires_refresh`、共享休息点 session、返回页面及取消机制沿用现有执行器，详见 [自动喝气泡水](resonance-pc-sparkling-water.md)。

## 便当子任务

当前任务引用：`tasks:bento_consumption_pc.yaml:bento_consumption_pc`；Action 为 `resonance_pc.consume_bentos_to_floor`。这是完整子任务，使用执行 facade 的任务通道调用，保留父子取消、业务结果与页面检查。

业务输入仅包括：

```json
{
  "eat_work_meals": true,
  "eat_love_bentos": true,
  "bento_priority": ["work_meals", "love_bentos"],
  "bento_start_threshold": 500,
  "bento_stop_threshold": 150
}
```

上例为调用示例，不是默认值。子任务先读取实际疲劳，只有严格高于开始线才消费。按已选择类型及顺序使用顶部工作餐或首个爱心便当；每份完成后重新读取实际疲劳，达到或低于停止线便结束。最后一份可以跨过停止线，不使用卡片标注或累加估算来提前决定已经恢复足够。

读取失败或无法确认消费后的疲劳时停止，不继续下一份，不把基础恢复量相减的结果冒充现场读数。部分已经消费的明细、记账及失败信息必须保留，不自动重跑整批。

`initial_fatigue` 为初始现场值，`final_fatigue` 为最新现场确认值，未知时为 null；`recovered_fatigue` 只在初始、最终实测值都可用时表示两者之差，否则为 null。`computed_fatigue` 不再作为控制或返回依据。

旧 `resonance_pc.consume_bentos` 仍是明确 `meals` 清单 Action。其历史说明见 [明确清单消费文档](resonance-pc-bento-consumption.md)，不能将该接口与当前阈值子任务混用。

## 数据、结果与失败

开跑前沿用现有一次恢复资源读取和有效 `recovery_snapshot` 交接。城市恢复检查优先使用交易现场读数和已确认路途累计，不因阈值判断重新扫描整份便当库存。固定先水后便当，喝水后重新读取实际疲劳并重新判断便当，便当保留逐份现场读取；这些新读数重新校准账本。已有资源记账和需要刷新的标记保持各自执行器语义。

共享货运 flow 完成每次恢复后合并结果；`auto_cycle_trade_pc.yaml` 的 `finish` 只接收 `trade_result`，不在 YAML 末尾再调用便当任务。输出包含：

- `recovery_events[]`：每次城市检查、触发条件、当前疲劳及其来源、恢复结果。`initial_fatigue_source` 标识进入检查时的来源，`fatigue_tracking` 保存检查结束时的账本快照。
- `sparkling_water_plan`：当前策略、开始/停止线及各次杯数计划。
- `sparkling_water`、`bento_consumption`：累计实际消费量与各次 `visits[]`，保留部分失败信息。
- `final_fatigue`：当前状态已经现场读取的实际疲劳。后续开始行车或产生未测量消耗时清空，不保留出发前的旧读数；仅有路途累计结果时也为 null。
- `estimated_fatigue`：来源为 `route_derived` 时的当前路途累计值；来源为现场读数或账本已失效时为 null。这个值可以用于恢复阈值判断，但不标记为实测疲劳。
- `fatigue_tracking`：最终账本快照。`current_fatigue` 是可用于当前判断的有效值，`source` 标识它是现场读数还是路途累计；没有可靠当前值时两者为空。

疲劳账本分别保存 `current_fatigue`、`source`、`last_observed_fatigue`、`last_observed_source`、`added_travel_fatigue` 和 `invalid_reason`。来源 `trade_page`、`profile`、`water`、`bento` 表示现场读数，`route_derived` 表示已确认路途累计；后者不能标记成现场实测。账本失效时公开当前值为空，历史读数只供排查，不参与下一次阈值判断。

例如交易结束读到 77，路段消耗为 100，确认普通到站后：`fatigue_tracking.current_fatigue=177`、`source=route_derived`、`last_observed_fatigue=77`、`added_travel_fatigue=100`；顶层 `estimated_fatigue=177`、`final_fatigue=null`。若之后喝水并现场读到 127，则新基准为 127、`source=water`、累计清零，顶层 `final_fatigue=127`、`estimated_fatigue=null`。进度资源中的 `actual_fatigue` 与 `estimated_fatigue` 按同一来源规则分开更新。

日志与进度沿用货运事件通道。未启用、未超过开始线、没有休息区、次数耗尽或无可用便当是正常跳过；交易页读取失败会转个人信息页兜底，兜底也失败、消费不明和返回页面失败保留错误。消费明细、路途累计与现场读数使用不同来源字段，不能用累计基础恢复量覆盖实测数据。

本次源码修改及离线测试不构成游戏中消费、GUI安装包或实机效果的验证记录。历史版本的验证不代表本规则已实机验证。
