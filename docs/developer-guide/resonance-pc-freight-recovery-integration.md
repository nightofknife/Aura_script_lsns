# PC 货运气泡水与便当接入设计

状态：已实现并通过离线回归，v1.9.6 CPU本地测试构建已替换桌面旧版；本轮不执行实机消费，实机效果待用户验证。
基线：2026-09-12，`1a8c980` 加当前工作区已实现的便当消费子任务。工作区其他未提交修改保持原样。
业务约定见 [到站恢复方案](resonance-pc-arrival-recovery-design.md)，消费接口见 [吃便当子任务](resonance-pc-bento-consumption.md)。

## 1. 已确定的边界

- 原有路线求解、利润计算、疲劳预算及界面原有预计疲劳算法不变。
- `8 * (S + ceil(S / 4))` 只作恢复时机和喝水量的简易消耗估算，不替换原求解器。
- 48点暂不参与任何计算，不扣路线预算，不计入后续消耗。
- 预算可行性由用户负责；不新增预算拦截、绕路、提前换恢复站或额外恢复次数。
- 沿用当前开跑前的一次恢复资源读取，不重复盘点便当。喝水节点、货运终点及消费后不刷新便当列表。
- 气泡水：最后一个有休息区的到站节点计算并执行。
- 便当：货运终点最后交易结束后，由货运父流程计算明确清单，只调用一次消费能力。
- 工作餐36，爱心便当用已核实基础值；不读取实际恢复量，不计算账号加成。
- 默认工作餐优先，其次临期爱心便当；类型顺序可调整。临期项放不下就跳过，不为凑数改变类型优先级。
- 消费子任务只接受 `meals`，只能从主界面开始；本地缓存、单目标定位和逐份记账保持现有边界。
- 不加“小任务”GUI，不给客运增加恢复逻辑，不改客运规划、参数或预算。
- 不添加旧字段兼容、配置迁移或与恢复无关的框架重构。

## 2. 总流程

```text
现有开跑前读取：当前疲劳、气泡水、工作餐、爱心便当 -> 保存本地
  -> 原路线求解器生成路线（不改变算法和预算）
  -> 父流程标记最后一个有休息区的到站节点
  -> 按原流程执行每段货运
       到达标记节点且开启自动喝水：
         父流程读取当前疲劳（只读疲劳）
         -> 计算剩余行车/协商消耗与喝水杯数
         -> 执行气泡水并返回城市面板
  -> 完成货运终点最后一次交易，确认回主界面
       开启自动吃便当：
         父流程只刷新当前疲劳
         -> 读取本地便当缓存，计算meals清单
         -> 清单非空时执行便当消费能力
         -> 确认成功并回主界面
  -> 货运完成；按原工作流继续客运或其他后续任务
```

两个恢复节点都由货运父流程控制，不移动到客运末尾。若喝水城市恰好是终点，顺序为到站喝水、终点交易、生成便当清单并吃便当。

## 3. 参数归属与GUI

货运参数新增两项：

| 参数 | 默认值 | 归属 |
| --- | --- | --- |
| `auto_bento` | false | 是否在货运收尾安排便当 |
| `bento_priority` | `[work_meals, love_bentos]` | 父流程选餐的类型顺序，支持只选一类，不允许重复或未知类型 |

沿用 `auto_sparkling_water` 和 `base_fatigue_reserve`（默认200）。恢复下限属于货运父流程，不传给便当消费子任务。

- GUI必须增加文字为“自动吃便当”的复选框，放在货运恢复选项区域、“自动喝气泡水”旁边，默认不勾选，对应 `auto_bento=false`。
- 快捷货运与完整参数页的这个开关双向同步并保存，复用当前GUI同步链，不另建一套状态。勾选只保存运行选项，不立即触发消费。
- 开启后仅在货运结束时由父流程计算便当清单并调用子任务；关闭时不触发便当收尾。纯客运页面不增加这个开关，“小任务”列表不增加吃便当入口。
- 类型顺序在完整货运参数中配置，用勾选和上下箭头调整；关闭开关保留设置值。
- 新参数只加到货运/组合货运输入，不加到客运输入。
- GUI单独货运入口在喝水或便当任一开关打开时，复用现有开跑前恢复读取流程；两项同时开启也只能读取一次。
- 已自带读取步骤的工作流不得再插入第二次刷新。现有统一开跑读取行为不在本次扩展改造。
- 试算排除恢复执行参数，不打开游戏页面、不读便当柜、不消费。
- 关闭便当开关不新增终点读取、缓存检查或消费调用；原有开跑读取不因此改变。

## 4. 模块分工

计划内纯计算模块 `_freight_recovery_policy.py` 只处理已提供的数据，不依赖app/OCR/vision，不读写缓存：

- `select_last_water_arrival(route, rest_lookup)`：找最后一个有休息区的到站节点。
- `estimate_remaining_consumption(route, arrival_index, travel_costs)`：枚举尚未执行的行车和协商，返回简易消耗与组成依据。
- `plan_water_use(current_fatigue, remaining_consumption, reserve, free_uses)`：算杯数及预计结余。
- `plan_bento_meals(current_fatigue, reserve, priority, cached_inventory, food_catalog)`：生成明确清单和跳过原因。

这些内部函数不公开注册，不修改原路线，不更新库存，不以预算可行性拒绝跑商。
`rest_lookup` 接受城市名并返回布尔值，父流程只将已知的无休息区错误转换为false，其他错误保留。
选点输出 `city_index`；消耗估算输入 `travel_costs` 为移动数据中的 `costs` 矩阵，输出 `remaining_consumption` 为D。

共享跑商flow负责读取实时疲劳、调用纯函数、执行恢复动作、发布进度、整合结果。
气泡水执行器保留逐杯确认和记账；便当执行器保留明确清单、本地缓存和单目标定位，不增加规划或盘点职责。

## 5. 气泡水选点

设路线城市节点为 `C0 -> C1 -> ... -> CL`，第i段为 `Ci -> C(i+1)`。

- 仅考察实际到站节点 `j=1..L`，不增加起点出发前喝水。
- 复用城市店铺配置中的 `rest` 位置，不新建城市白名单。
- 选择最大的、具备休息区的 `j`。重复城市按到达索引区分。
- 没有路线、没有候选城市或免费次数为0时正常跳过。
- 到达选定节点后才最终计算杯数。结果为0则跳过，不回退到更早城市、不增设第二次恢复。
- `blocked`、到站失败、未确认城市状态时不执行恢复。

## 6. 剩余消耗估算

当前执行结构是：在一段的出发城市做卖货/买货，再行车；到站恢复发生在下一次城市交易之前。因此在 `Cj` 喝水时：

- 已执行的行车和协商不计入D。
- 剩余行车为段 `j..L-1` 的城市移动表成本之和。
- 尚未执行的买货砍价来自段 `j..L-1` 的 `bargain_to_cap`。
- 尚未执行的卖货抬价来自段 `j-1..L-1` 的 `raise_to_cap`：包含当前城市出售刚到货物，以及终点最后一批货物。
- 只统计路线明确安排、尚未执行的协商，不因进入交易所就虚构一次协商。

设尚未执行的砍价/抬价总轮数为M：

```text
S = 2 * M
estimated_failures = ceil(S / 4)
estimated_negotiation_cost = 8 * (S + estimated_failures)
D = remaining_travel_cost + estimated_negotiation_cost
```

对这份剩余操作集合整体向上取整，不对每轮/每个城市分别取整再相加。1轮24，2轮40，3轮64，4轮80。
在终点、最后交易之前，剩余行车为0，但最后一轮抬价仍可能使D为24，而不是直接把D设为0。

这个D不取自原求解器的 `remaining_expected_fatigue` 或 `expected_fatigue_used`，也不覆盖这些字段。原求解器仍保留原来的概率/期望疲劳口径。
实际已发生的协商差异反映在父流程现场读取的F中，不把历史协商再算一遍；后续协商只使用上述简易模型。
不把48缓冲、尚未吃的便当、假设会用的疲劳药或预算余额计入D。

## 7. 到站读取疲劳与计算喝水量

复用现有 `resonance_pc.player_data_refresh`，仅传：

```json
{"stages": ["profile"], "profile_sections": ["fatigue"]}
```

父流程先将城市面板返回主界面，再调用只读疲劳的流程，确认其返回主界面并取得本次有效数值。此调用不会选择工作餐或爱心便当数据段，不进入便当柜，不扫描列表。
之后现有喝水执行包装器从主界面打开城市面板执行，沿用原返回城市面板的约定。

令F为本次读取的当前疲劳、R为恢复下限、N为有效的剩余免费次数：

```text
K = max(0, min(N, (F - 1) // 50, (F + D - R) // 50))
```

等价要求：`K<=N`、`F-50K>0`、`F-50K+D>=R`。全部使用整数，不用浮点近似处理边界。
喝水后当场可以低于R，但不能到0或以下。K=0为正常跳过，不引发预算纠正。

`F=401,D=100,R=200,N=6`：K=6，当场101，预计货运完成后201。
`F=250,D=0,R=200,N=6`：K=1，预计剩200。
`F=50,D=300,R=200,N=6`：K=0，不能当场喝到0。

杯数确定后调用现有逐杯执行器，不用新增点击流程。执行器再次检查本地免费次数，消费确认后逐杯扣减；提前耗尽按现有返回原因处理，不购买付费次数。

## 8. 货运终点便当规划

触发点为共享 `resonance_pc_auto_cycle_trade_flow` 中的最终交易流程成功结束之后、整体成功结果返回之前。
先确认主界面，再只刷新当前疲劳F；不复用开跑时疲劳，不重复盘点便当。

1. 若F不高于R，生成空清单并正常跳过，避免不必要的便当缓存检查。
2. 父流程读取本地 `recovery.work_meals`、`recovery.love_bentos`，只校验启用类型；不扩张气泡水的 `recovery_snapshot` 来传整份便当列表。
3. 缓存缺失、无效或标记需要刷新时报告，不能以运行中的自动盘点补齐。
4. 复用现有数据验证/身份解析，按父参数类型顺序排列候选；工作餐按时段，爱心便当按剩余天数、角色ID、菜品ID。
5. 设置额度 `A=max(0,F-R)`。遍历每个可用候选：恢复量不大于A则加入清单并扣A，否则跳过继续。
6. 工作餐用36，爱心便当用 `love_bento.json` 基础恢复量。评分保持由消费子任务按菜品ID处理。
7. 输出只含身份字段的 `meals`，每条一份，不含疲劳、下限、评分、恢复量或坐标。
8. 清单为空正常结束；非空仅调用一次便当消费能力。子任务逐份执行清单，不重新计算数量。

例如F=300、R=200、有两份工作餐及基础恢复20的爱心便当：先选两份工作餐，额度100->28，再选该爱心便当，计划结余208。
类型顺序反转时按新顺序重新计算；不使用全局背包优化打乱优先级。
临期项放不下时跳过，继续选下一份放得下的条目；不把“缓存需要刷新/数据损坏”当作“放不下”。

此处下限保证是按用户指定的基础恢复值做计划，不读取或补偿账号加成，不把计划结余冒充实测结余。父任务若另有实际疲劳展示需要，应单独刷新；本次不为了追加便当循环刷新疲劳。

## 9. 框架调用与取消

当前单独货运与组合货运都调用共享flow，因此恢复钩子放在这个flow中，不只在GUI按钮或单独货运YAML末尾追加。

从异步flow调用现有同步的疲劳读取和便当消费Action时，采用框架 `ActionInjector.execute` 的注册Action调用通道，按现有 `NodeExecutor` 构造方式提供当前context、renderer、engine及service resolver：

- 疲劳读取Action：`resonance_pc.player_data_refresh`，只传profile/fatigue。
- 便当执行Action：`resonance_pc.consume_bentos`，只传meals。
- 这样保留参数注入、当前CID、取消标记和同步worker完成计数，不用裸 `asyncio.to_thread` 绕过取消等待。
- 当前flow开头丢弃context，实施时需保留用于上述调用；不新建scheduler或runner。
- 其他YAML父任务仍可通过 `aura.run_task` 调用已注册的便当子任务。

注意：当前 `ActionInjector` 的 `aura.run_task` 分支返回的是 `framework_data`，不能假定它直接返回子任务的业务user_data。共享flow采用注册Action调用取得业务字典，不修改框架的返回契约。

所有恢复返回都必须检查业务 `success` 和最终页面，不能只检查框架节点成功。便当失败可能已经消费部分餐，必须保留明细，不能自动重跑整批。

## 10. 组合客货运边界

- 在组合货运输入白名单、嵌套schema及参数转发中加入 `auto_bento/bento_priority`；不加入客运参数。
- `persistent_data` 依赖不能继续只按是否传入气泡水快照决定。仅开启便当时也必须能读本地库存并记账。
- 货运在前：货运收尾吃便当，返回主界面后继续原客运流程。
- 客运在前：保留原客运执行与货运交接，货运结束再吃便当。
- 纯客运任务完全不触发本功能。
- 原组合疲劳预算计算不改，便当恢复量不回补到客运预算。
- 父组合不再加第二次吃便当调用。
- 恢复失败或页面未知按既有工作流失败/取消原则处理，不能为了继续客运而在未知页面盲点；不借此新增客运恢复能力或修改客运业务规则。

## 11. 结果与可观察性

保留原路线结果、预计疲劳、实际协商统计等字段，新增或扩充恢复专用字段：

- `sparkling_water_plan`：选定到站索引、城市、F/D/R/N、剩余行车、协商轮数、简易协商成本、杯数、喝完即刻及预计终点疲劳。
- `sparkling_water`：沿用实际执行结果，杯数与已确认消耗保留。
- `bento_plan`：现场读取的F、R、类型顺序、本地数据时间、meals清单、计划基础恢复量、计划结余及跳过原因。
- `bento_consumption`：消费Action原样结果，包括已确认份数、已完成份数、页面和部分失败明细。

日志/进度复用货运现有通道：选择喝水节点、计算杯数、喝水开始/结束、读取终点疲劳、生成便当清单、消费开始/结束。
空清单/零杯/未开启是正常跳过，不能显示为报错。数据读取失败、结果不明、返回失败为错误，不伪装成无库存。
界面明确区分原路线预计疲劳、恢复简易估算和实际消费份数，不能混用口径。
