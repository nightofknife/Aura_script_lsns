## 1. 功能范围

在 PC 跑商中增加可选的自动吃便当能力，与自动喝气泡水配合。
当前采用两个固定阶段：

1. 在本次跑商路线中最后一个能喝气泡水的城市集中喝水。
2. 到达终点并完成最后交易后，集中吃便当。

便当在任何城市都能吃，但本版只在终点安排。终点若也是喝水城市，则先完成喝水阶段，再按终点实际疲劳计算便当用量。

不再采用早先讨论的“所有恢复只能在同一个城市完成”，也不做复杂的恢复城市与路线联合优化。

## 2. 用户负责预算可行性

预算是否合理、能否撑到最后一个喝水城市，由用户自行判断。
本次不新增预算可行性检查，不因恢复规划而拒绝执行、纠正预算、修改路线、提前恢复或增加其他恢复站点。
不要重新加入“到达喝水城市前可能达到疲劳上限，因此自动换点或报方案不可行”的逻辑。
现有运行错误、截图失败和取消处理，不属于预算可行性检查。

## 3. 疲劳口径

- 跑商疲劳预算：整趟允许累计消耗的疲劳；恢复不会退回已经消耗的预算。
- 恢复下限：沿用现有 `base_fatigue_reserve` 设置，默认 200。
- 协商缓冲：48点暂不参与任何计算，不从路线预算扣除，不计入后续消耗，不据此增加预算拦截。
- 预计后续消耗应包含尚未执行的行车和协商，不能只累计行车。

### 协商成本

以下只用于恢复时机及喝水量的简易消耗估算，不替换现有跑商疲劳算法、路线求解器或界面原有的预计疲劳计算。

每轮砍价或抬价按两次成功操作计算；成功操作合并计数，每四次成功计一次失败，不足四次向上取整。成功和失败每次都计 8 疲劳。

```text
S = (砍价轮数 + 抬价轮数) * 2
预计失败数 = ceil(S / 4)
预计协商疲劳 = (S + ceil(S / 4)) * 8
```

| 协商安排 | 成功操作数 | 预计失败数 | 疲劳 |
| --- | ---: | ---: | ---: |
| 无协商 | 0 | 0 | 0 |
| 一次抬价或砍价 | 2 | 1 | 24 |
| 一次抬价和一次砍价 | 4 | 1 | 40 |
| 合计三轮 | 6 | 2 | 64 |
| 合计四轮 | 8 | 2 | 80 |

一次抬价和一次砍价不能分别向上取整后算成 48。此规则取代恢复估算中之前讨论过的“每轮固定16”或“每轮固定24”，不改变实际协商执行策略。

## 4. 气泡水阶段

选取路线中最后一个能喝气泡水的城市，不再按旧逻辑选“杯数最多时的最早节点”。
气泡水每杯恢复 50，只使用剩余免费次数。

设：

- `F`：在喝水城市准备喝水时的疲劳。
- `D`：从此刻到整趟跑商结束，尚未执行的预计行车与协商消耗，包括尚未执行的终点交易协商。
- `R`：恢复下限。
- `N`：剩余免费气泡水数量。
- `K`：本次喝水杯数。

选择满足以下条件的最大正整数 `K`；不存在可用正整数时不喝：

```text
K <= N
F - 50 * K > 0
F - 50 * K + D >= R
```

喝完当场允许低于恢复下限，但不能喝到 0 或以下；下限约束的是加上后续消耗后的终点疲劳。不能把还没吃的便当恢复量或 48 点缓冲算进 `D`。

### 用户给定示例

恢复下限 200；B 城疲劳 401，剩余六杯气泡水；B 城喝水之后到 C 城跑商完成，还会消耗 100：

```text
只喝四杯：401 - 200 + 100 = 301
喝六杯：  401 - 300 + 100 = 201
```

应喝六杯。不能用“喝完当场必须保留 200”的旧算法限制为四杯。

## 5. 终点便当阶段

完成终点交易后，按当时实际疲劳重新计算用量；此时不预加任何后续跑商消耗。

- 默认优先级：工作餐，然后爱心便当。
- 便当使用优先级可调整；气泡水已固定为前一执行阶段，本版不跨阶段混排三类资源。
- 工作餐每份固定恢复 36。
- 爱心便当恢复量取决于菜品种类，使用已核实的 `food_id -> FoodFactory基础恢复点数`。用户明确不读取实际恢复量、不计算账号加成；工作餐保持固定36。
- 爱心便当内部按剩余保质期从短到长优先使用。
- 临期便当恢复量放不下时跳过，在其余能完整使用的候选中继续按临期顺序选择。
- 吃多少是多少，尽可能接近恢复下限，但每份完整使用后都不能低于下限。
- 不能因为还有便当就强行吃完，也不能把不确定的识别结果当作可消费库存。

例如终点实际疲劳 201、恢复下限 200，则不再吃恢复 36 的工作餐。

便当恢复只挂在货运结束时，不延后到整个客货运组合结束。若顺序为货运先、客运后，货运收尾吃完再继续原有客运流程；不向客运添加恢复步骤，不修改客运参数、规划或预算，也不把便当恢复量补给客运预算。

## 6. 当前代码基础

- 工作餐读取结果为 `recovery.work_meals`：数量和三个时段槽位状态。
- 爱心便当读取结果为 `recovery.love_bentos`：数量、条目及更新时间；条目包含角色 ID/名称、菜品 ID/名称、剩余天数。
- 爱心便当扫描目前按 `(role_id, food_id, remaining_days)` 去重，不保存可直接用于食用的定位坐标。
- 本次已在现有菜品目录中补齐有来源依据的基础恢复量和评分规则。
- 当前跑商恢复快照投影未传爱心便当明细；后续功能需要接通实际所需数据。
- 读取与消费保持分离；子任务负责食用、评分、确认消耗和更新库存，由货运父流程在最终交易后按明确清单调用。

## 7. 用户说明的便当使用流程

吃便当任务和公开 Action 只能从主界面开始，并先确认主界面。进入便当柜沿用现有入口；跑商或其他调用方需先返回并确认主界面，不能从城市面板或便当柜直接调用。每次只点击单份“使用”，不点击“全部使用”，不勾选“今日不再提示”。

### 工作餐

1. 选择要吃的工作餐，确认右侧单份“使用”按钮为蓝色可用状态。
2. 点击“使用”，在使用确认框点击“确认”。
3. 等待食用动画和疲劳恢复效果界面，点击空白区域退出。
4. 回到便当柜；刚吃掉的槽位变为空槽，当前选中项的“使用”按钮变成灰白禁用状态。
5. 重新选择下一份可用工作餐，不重复点击已消耗项。

未到发放时间的工作餐被选中时，没有单份“使用”按钮；“全部使用”仍可能存在，不能用它判断当前选中项可用。

### 爱心便当

1. 选择目标爱心便当，点击单份“使用”，在确认框点击“确认”。
2. 等待食用动画与疲劳恢复效果界面，点击空白区域退出效果界面。
3. 进入评分界面，按菜品种类选择一星或五星，确认星级已选中后点击评分“确定”。
4. 回到便当柜后才继续下一份；消费后重新定位目标，不能假设列表位置不变。

评分规则以用户随后提供的菜品总览图修正为准：图中前两个黑色菜品给一星，其余九种已知菜品给五星，判断依据是菜品 ID 而非赠送角色或泛化的颜色判断。

| 菜品 | food_id | 评分 |
| --- | --- | --- |
| 菜肉俱全汉堡 | 83300002 | 1 星 |
| 焦香水果派 | 83300011 | 1 星 |
| 当前目录其余九种菜品 | 其余已知 ID | 5 星 |

此规则取代此前仅把菜肉俱全汉堡列为一星的记录；不得扩展为所有汉堡或所有水果派都给一星。

消费已确认但评分未完成时，只能继续处理评分/返回，不能重新执行使用流程，以免额外消耗。
全部吃完或无法在恢复下限内继续吃时，从便当柜点击左上角火车图标回主界面，不逐层点击返回箭头。
