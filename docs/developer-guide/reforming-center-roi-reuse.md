# 改造中心房间扫描：单次 ROI 灰度复用

## 范围

第三批第一步只修改 `_reforming_center_room_templates.py` 的房间扫描路径。一次 `room_hits` 中，同一张输入图、同一实际裁剪区域只成功转换一次 ROI 灰度。下一次 `room_hits` 无论传入新图还是同一个数组，都重新计算。

`match_asset(image, spec, region=None)` 的签名和独立调用行为保持不变。模板原图缓存、模板灰度转换、标准差计算、匹配算法、阈值、非有限值清理及坐标输出均保持原样。

## 生命周期与处理顺序

`room_hits` 使用 ContextVar 绑定本次观察的 `(image, gray_rois)`，在 `finally` 中恢复之前的上下文。线程分别持有上下文；嵌套扫描结束后恢复外层扫描。默认没有绑定，因此其他业务独立调用 `match_asset` 仍逐次计算 source 灰度。

只有输入对象与本次观察一致时才使用该缓存，键为按原规则解析、裁剪后的 `(x, y, width, height)`。不同区域分别准备；缓存不通过 ndarray id 跨调用复用，也不跨截图、点击或拖动保存。

每个模板仍遵循原处理顺序：

1. 解析 region，按现有 1280×720 上界处理坐标。
2. 加载模板，取得当前 source 的 `:3` 通道裁块。
3. 转换模板灰度。
4. 在原 source 灰度转换位置，首次计算或复用该 ROI。
5. 检查尺寸；仅尺寸足够时计算模板标准差。
6. 按原方法匹配、清理非有限分数并判断阈值。

灰度转换成功后才写入缓存，转换异常不保存为失败条目。空目录不会提前读取或转换图像；缺失资产、坏 source 切片和转换错误仍在原有位置抛出，不增加异常包装。

保持先裁剪再灰度，不改为整帧转换后切片。房间和 variants 遍历顺序、每房间最高分及其并列处理、同位置名称竞争的 overlap 和分差规则也不变。

## 性能与验证

当前目录有 28 个房间、30 个地图标题候选。默认扫描使用同一块 1250×490 ROI，因此正常一轮的 ROI 灰度转换从 30 次降为 1 次；模板侧处理仍为原次数。这个调用次数变化不能直接等同于整轮提速比例。

新旧差分以本轮实施前工作区源码快照为 oracle，比较真实总览、保存的仓库抗锯齿截图、平移和合成负例、不同 ROI、异常优先级及顺序。回归同时覆盖共用 `match_asset` 的车间观察入口。

耗时对比单独记录完整 `room_hits`、灰度转换阶段以及模板缓存清理后的首次扫描。统计灰度调用次数与实际耗时测量分开执行，避免插桩开销污染计时。测试均为离线截图，不包含 WGC、游戏输入或等待动画。

## 本次实测

ROI-only 源码版本 SHA256 为 `867d18c8c0032e6a37abc8301836d699b1a46c1b520d737f27b5f05f799f3a1d`。该版本相关 pytest 为 234 项通过，245 项识别、异常、顺序和调用次数差分无差异。四张计时截图均确认 source 灰度转换 30→1；模板灰度、模板标准差和 `matchTemplate` 仍各执行 30 次。

OpenCV 4.13.0 使用原有 32 线程配置。每组 30 对新旧交错采样，计时不带调用计数插桩。下表为中位数：

| 截图 | 完整扫描：旧→新 ms | 仅 ROI 灰度：旧→新 ms |
| --- | ---: | ---: |
| overview_00 | 196.418→193.923 | 0.838→0.028 |
| overview_02 | 193.325→192.316 | 0.842→0.027 |
| overview_04 | 201.916→203.519 | 0.793→0.026 |
| live_warehouse_20261011 | 220.812→222.468 | 0.874→0.030 |

减少重复灰度转换的收益明确，但完整扫描变化约为慢 0.8% 到快 1.3%，不能据此认定稳定提速。完整扫描仍主要耗时于匹配运算。冷模板缓存组只清 Python `_asset` 缓存，不清操作系统文件缓存。

原始报告位于 `.pytest_tmp/template-match-batch3a-f96f885333ad4a39960e12eb5f62021c/differential-benchmark-report.{json,md}`，含各组 p95 和原始样本。运行末尾检测到另一个对话将共享文件改成服务注入版本，247 项总检查中的源码未变检查因此失败；原始报告保留该失败。上述结果只对应启动时加载的 ROI-only 版本，不能用于验收后续服务迁移。

协调完成后，收菜缓存与框架注入分别迁至独立模块。框架迁移对话确认消费者解除并授权恢复共享文件；恢复后的源码哈希与上述已测版本完全一致，素材和 fixture 哈希也再次确认一致。交接证明单独保存在同目录 `handoff-validation.{json,md}`，没有覆盖原报告中的漂移记录。
