# PC 自动喝气泡水

## 入口与数据

快捷货运设置和完整货运参数页使用同一个 `auto_sparkling_water` 开关，默认关闭。
原货运疲劳药控件已被替换；客运的疲劳药配置保持原行为。
整套流程仍强制刷新 `profile` 中的 `fatigue`、`sparkling_water`、`bento`。
完整货运页单独运行且启用自动喝水时，同样先刷新这些数据。

运行输入 `recovery_snapshot` 是本次刷新返回的 `player_data`，包含：

```json
{
  "status": {"fatigue": {"current": 1, "max": 856}},
  "recovery": {"sparkling_water": {"remaining_free_uses": 6, "daily_free_limit": 6}},
  "metadata": {"persisted": true}
}
```

开启自动喝水但缺少有效快照时，在操作 UI 前失败，不从旧缓存补齐。
本地方案预览不刷新游戏、不消费此快照。
客运先于货运时，组合任务把已完成客运的移动疲劳加到快照副本中；原快照不变。

## 选点

起点为节点 0，第 k 段的到站城市为节点 k+1。相同城市的不同抵达分别计算。
城市具备 `location_pc.json` 中的 `rest` 坐标才可候选，不另维护城市名单。

设初始疲劳为 F0，剩余次数为 N，累计移动疲劳为 T：

```text
F = F0 + T
K = min(N, max(0, (F - 1) // 50))
```

选择 K 最大的节点，杯数相同时选最早节点。严格要求 `F > K * 50`。
初始 1、全程移动 200 且终点有休息区时喝 4 杯；只有累计移动 100 处有休息区时喝 2 杯。
零剩余次数、无法喝一杯或没有休息区则跳过。不绕路、不扩大路线预算。
只累计城市移动表的疲劳；协商、疲劳药和便当不纳入这版选点计算。

## 独立任务

任务引用：`tasks:sparkling_water_pc.yaml:sparkling_water_pc`。
输入示例：`{"city_name":"岚心城","drink_count":2}`。
起始和结束页面均是显示店铺位置的城市地图 `city_panel`。
执行前需要 `user-data/user-info.json` 中已有有效的气泡水剩余次数；请求杯数不得超过记录。

执行顺序：城市配置坐标进入休息区、杯子图标进入饮品菜单、气泡水杯子图标、
可选的蓝底确认勾选图标、固定坐标点击 SKIP、菜单返回。
每个点击先确认原目标消失，再等待目标页面。只有原目标仍明确存在时才补点，最多三次。
普通识别最多 3 秒、间隔 0.4 秒，点击后间隔 0.5 秒；动画退出最多 15 秒。
动画阶段不识别 SKIP，固定点击 `[1207,36]`，并检查交谈图标或气泡水图标是否重新出现。
图二退出时先返回图一，再返回城市；图一直接返回城市。返回箭头复用原模板。
最后复用小区域城市 OCR 确认同一城市，其余菜单均使用批准的图标模板。

每杯以选项消失、随后菜单返回确认完成，通过 `core/persistent_data` 立即更新剩余次数。
点击气泡水前先标记 `requires_refresh`，确认完成后清除；如果在动画中取消或中断，
独立任务会拒绝复用未确认的次数，直到现有用户数据刷新替换该项数据。
如果提前返回图一，按照游戏次数耗尽的行为把剩余次数记为零，并记录提前结束原因。
页面或截图失败不作为目标消失，失败时不重跑整批。取消后不继续点击。

## 结果与诊断

跑商结果新增 `sparkling_water_plan`（各节点计算依据及最终选择）和 `sparkling_water`（实际结果）。
到站触发结果也保存在 `execution.leg_results[].sparkling_water`；起点结果保存在
`execution.sparkling_water`。运行进度事件使用现有货运事件通道，阶段为 `sparkling_water`。

日志前缀为 `Sparkling water`。INFO 记录选点、每杯确认、剩余次数及最终结果；
DEBUG 记录图标置信度和点击坐标；ERROR 记录失败阶段、最后页面和已完成杯数。
正常返回城市后才继续下一段或终点清仓。

离线测试使用提供截图中的小区域 fixture，覆盖真实框架匹配、局部重试、两种确认路径、
连续喝水、返回、持久化、路线选点及 GUI/组合任务交接。实机仍需确认其他休息区城市
的菜单位置及不同动画下的退出表现。
