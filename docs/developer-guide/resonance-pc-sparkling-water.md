# PC 自动喝气泡水

## 入口与阈值

快捷货运设置和完整货运参数页使用同一个 `auto_sparkling_water` 开关，默认关闭。开始线 `sparkling_water_start_threshold` 和停止线 `sparkling_water_stop_threshold` 默认分别为 600 和 100，用户可以修改；启用时必须满足整数 `start > stop >= 0`。

货运起点、每次成功到站、城市交易后出发前及最终交易后的安全节点使用最新有效疲劳：交易页现场读取或普通到站路途累计，失败或特殊情况再兜底读取。只有 `F > start` 才喝水，等于开始线时不喝；不因预计后续行车或协商消耗提前触发。每个检查点独立判断，不固定选择最后一个休息区。恢复方式固定先气泡水后便当；喝水结束后按最新实际疲劳重新判断便当，便当类型按 `bento_priority` 排序，整体顺序见 [货运恢复接入](resonance-pc-freight-recovery-integration.md)。

原 `base_fatigue_reserve` 和剩余消耗预算不再参与杯数计算。城市必须具备 `location_pc.json` 中的 `rest` 坐标；没有休息区或免费次数为零时跳过，不绕路、不购买次数。

## 数据与杯数

沿用现有开跑前 `profile` 恢复数据读取及有效 `recovery_snapshot`，输入示例：

```json
{
  "status": {"fatigue": {"current": 1, "max": 856}},
  "recovery": {"sparkling_water": {"remaining_free_uses": 6, "daily_free_limit": 6}},
  "metadata": {"persisted": true}
}
```

开启自动喝水但缺少有效快照时在操作 UI 前失败，不从旧缓存补齐。快照用于资源交接，不替代城市检查时的实际疲劳读数。试算不刷新游戏、不消费快照；客运在前时的组合交接不授权按预计疲劳触发喝水。

设现场疲劳 F、停止线 S、有效剩余免费次数 N；满足开始条件后：

```text
needed = ceil((F - S) / 50)
drink_count = min(N, needed, (F - 1) // 50)
```

每杯固定恢复 50，最后一杯允许跨过停止线；喝后疲劳必须大于 0，停止线为 0 时也一样。次数不足或不能再安全喝一杯时停止。杯数不使用剩余行车、协商、预算余额或预计终点疲劳。

例如开始线 600、停止线 370，现场疲劳 600 不触发，621 在有 6 次免费次数时计划 6 杯；只有 4 次免费次数则最多喝 4 杯。喝完后重新取得实际疲劳，再独立判断便当的开始条件。

## 独立任务

任务引用：`tasks:sparkling_water_pc.yaml:sparkling_water_pc`。输入示例：`{"city_name":"岚心城","drink_count":2}`。独立任务仍接收明确杯数，阈值判断属于货运父流程。

起始和结束页面均是显示店铺位置的城市地图 `city_panel`。执行前需要 `user-data/user-info.json` 中已有有效的气泡水剩余次数；请求杯数不得超过记录。

执行顺序：城市配置坐标进入休息区、杯子图标进入饮品菜单、气泡水杯子图标、可选的蓝底确认勾选图标、固定坐标点击 SKIP、菜单返回。
每个点击先确认原目标消失，再等待目标页面。只有原目标仍明确存在时才补点，最多三次。
普通识别最多 3 秒、间隔 0.4 秒，点击后间隔 0.5 秒；动画退出最多 15 秒。
动画阶段不识别 SKIP，固定点击 `[1207,36]`，并检查交谈图标或气泡水图标是否重新出现。
图二退出时先返回图一，再返回城市；图一直接返回城市。返回箭头复用原模板。
最后复用小区域城市 OCR 确认同一城市，其余菜单均使用批准的图标模板。

每杯以选项消失、随后菜单返回确认完成，通过 `core/persistent_data` 立即更新剩余次数。
点击气泡水前先标记 `requires_refresh`，确认完成后清除；如果在动画中取消或中断，独立任务拒绝复用未确认的次数，直到现有用户数据刷新替换该项数据。
如果提前返回图一，按照游戏次数耗尽的行为把剩余次数记为零，并记录提前结束原因。
页面或截图失败不作为目标消失，失败时不重跑整批。取消后不继续点击。

## 结果与诊断

货运结果保留 `sparkling_water_plan` 和 `sparkling_water`，按城市检查累计 `visits[]`；`recovery_events[]` 记录每次检查的实际疲劳、阈值和结果。`final_fatigue` 是最新实际确认值，未知时为 null，不能用喝水杯数估算值补齐。

运行进度沿用货运事件通道。日志前缀为 `Sparkling water`；记录阈值判断、每杯确认、剩余次数、返回页面和失败阶段。正常回到预期城市页面并完成必要读数后，才继续便当判断、交易或下一段。

历史截图回放和旧选点测试不证明当前阈值策略已实机验证。此次修改不执行游戏内消费或发布。
