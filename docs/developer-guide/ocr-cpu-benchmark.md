# OCR CPU benchmark

使用真实 PP-OCRv6 small ONNX 模型比较 OCR 的 CPU 线程与自旋策略。

运行命令（仓库根目录，输出目录应为本轮独立目录）：

```powershell
$benchmarkTemp = Join-Path $PWD '.pytest_tmp/ocr-cpu-benchmark/matrix'
New-Item -ItemType Directory -Force -Path $benchmarkTemp | Out-Null
$env:TEMP = $benchmarkTemp
$env:TMP = $benchmarkTemp
$env:TMPDIR = $benchmarkTemp
& ./.venv/Scripts/python.exe -m tools.benchmark_ocr_cpu --output .pytest_tmp/ocr-cpu-benchmark/matrix
```

基准包含自动、1、2、4、8 个 ORT 算子内线程与自旋开关，共十种配置。
每种配置在独立子进程中创建检测、方向分类和识别三个会话，串行运行；
两轮采用不同的配置顺序。每个样本预热三次，每轮连续调用二十次，
另间隔 150 ms 调用八次。

样本来自现有真实截图：

| 场景 | 来源 | 输入大小 |
|---|---|---|
| 数字单行直接识别 | `tests/fixtures/profile_status_digits/clarity_258_286.png` | 99×25 |
| 中文单行直接识别 | `tests/fixtures/raw_workshop_ui/idle_blue.png`，裁剪 `(354,16,280,44)` | 280×44 |
| 小区域完整 OCR | `tests/fixtures/city_identity/main_visit_roi.png` | 250×70 |
| 大图完整 OCR | `tests/fixtures/raw_workshop_ui/idle_blue.png` | 1280×720 |

计时包含图像预处理、模型执行、后处理和结果解析，不含截图、文件读取、
会话加载及异步桥接。采用框架当前默认检测尺寸上限与批处理策略。
OpenCV 线程策略保持不变；ORT 的线程数不表示整个进程的线程上限。

输出包含各次原始延迟、P50/P95、进程 CPU 时间、间隔内 CPU 时间、
识别文本、输入文件 SHA256、运行环境、会话加载耗时和线程数量。
CPU 时间是所有进程线程的累计时间，可超过对应的墙钟时间。
Windows CPU 计量存在粒度限制，接近零的微小差异不宜过度解读。

`summary.csv` 供比较，`run-*.json` 保留每轮原始数据。
完成后可用 `--summarize-only` 重新汇总并核对跨配置文本一致性。

## 2026-10-22 本机结果

环境：AMD Ryzen 9 9950X，16 物理核、32 逻辑处理器，Windows，ONNX Runtime 1.27.0，
CPUExecutionProvider，OpenCV 配置为 32 线程。模型为当前 PP-OCRv6 small。
两轮共 20 个独立 worker、2240 次计时识别；每种配置每个样本有 40 次连续调用、
16 次间隔调用，另有预热。四类样本分别返回 1、1、3、40 个文本区域。
所有配置的识别文字、区域数量在重复调用、跨轮次与跨配置比较中均一致。
这是一致性检查，不是带标注的准确率评估。

每次连续调用的进程 CPU 时间（CPU-ms，多线程累计）：

| 配置 | 数字单行 | 中文单行 | 小区域 | 大图 |
|---|---:|---:|---:|---:|
| 自动/开 | 66.80 | 73.83 | 2004.30 | 7599.61 |
| 4/关 | 19.14 | 22.27 | 77.34 | 1775.39 |
| 8/关 | 26.56 | 30.47 | 106.25 | 2292.19 |

间隔 150 ms 调用时，8/关相较自动/开的每次调用周期 CPU 成本减少约
69.7%～94.6%。以小区域为例，周期 CPU 时间从 1987.30 降至 107.42 CPU-ms；
等待间隔部分从 738.28 降至接近计量下限，不能将其解读为系统 CPU 完全为零。

本机推荐：8 个 ORT 算子内线程、关闭自旋。
它相较自动/开，小区域延迟下降约 68.3%，大图延迟仅增加约 1.5%，
对应 CPU 时间减少约 94.7% 和 69.8%；单行识别增加约 1.2 ms。
4/关可作为更省 CPU 的选项，但大图中位耗时比 8/关多约 130 ms。

完成基准后，框架 OCR 已采用 8 线程、关闭自旋作为默认配置，
并保留线程数和自旋的独立配置覆盖，见 [Framework OCR](./ocr-service.md)。
不能直接将本机的 8 线程结论推广到低核 CPU；未测试游戏共载下的响应。
两轮存在耗时波动，原始数据保留于 `.pytest_tmp/ocr-cpu-benchmark/matrix/`。
